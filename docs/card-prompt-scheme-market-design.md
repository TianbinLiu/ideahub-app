## A. 提示词方案市场 + 灵活图位

### A0. 从三套参考素材读到的共性

用户给的三张截图是三套「人物卡设定图」提示词：
1. **思路2「风格转绘、人脸和服装分离」**：素描线稿头部 + **无面部白模三视图**（mannequin head, blank face）。产出里**故意不含可辨认人脸**——身体/服装走写实、头部是白模台。
2. **实操案例**：带 `{{角色类型，职业女性}}` 占位的通用设定图，产出=头部视图组 + 全身正交转体组 + 补充视角组（半身/俯视）。
3. **思路2「面部特写+全身三视图+6肖像」**：21:9 超宽、纯白棚拍、写实，产出=面部特写 + 全身三视图 + 6 张肖像。

**关键结论**：不同方案产出的**图位数量与种类都不同**——有的没有「标志性细节」，有的一次出 6 张肖像，有的整套无脸。所以现在写死的三格（全身立绘 / 面部特写 / 标志性细节）确实太硬。这正是要做 A 的产品理由，**与 B 无关**。

### A1. 现状（本文写作时）

- `types.ts` `CardView.kind: "face" | "body" | "detail"`——**三值写死的联合类型**。
- `CARD_SLOTS[type]`——每种卡的槽定义（character 三槽、其余两槽），槽自带 `label`（"全身立绘"）与 `locks`（"服装、体型与整体配色"）。
- `viewsOf(card)`——**全仓唯一的形象参考归一处**（铁律六）：老卡缺 `views` 时兜底成「卡面即主图」。
- `ai/real.ts` `allocateRefs` / `refUsedFlags`——**"哪几张图真喂给 Seedance" 的唯一实现**，排序键 `KIND_ORDER = {face:0, body:1, detail:2}`；详情页/命名屏的「出片用 / 仅展示」全从 `refUsedFlags` 取。
- `portraitViews`（上一版刚加）——写死出 body + face 两张。

### A2. 数据模型的**核心决定**：`role`（机器读）与 `tag`（人读）分家

灵活化的陷阱在这里：`refUsedFlags`/`allocateRefs` 现在**靠 `kind` 判断哪张锁脸、哪张锁身、哪张只展示**。tag 一旦变成自由文本，管线就没法再回答"这张图在出片里干什么"。所以**不能**把 `kind` 直接换成自由 tag。要拆成两位：

- **`role`（受控词表，机器读）**：`"primary" | "face" | "aux" | "display"`。它替代今天 `kind` 的**语义**职责——`allocateRefs` 的取图顺序与 `refUsedFlags` 的「出片用」判定全部改读 `role`，**仍只有这一处实现**（铁律六）。`primary`≈今天的 body（锁主体/服装）、`face`≈锁脸、`display`≈今天 detail 那种「只展示、不进模型」、`aux`=进模型的额外参考（给"6 肖像"这种留口，但受 `MAX_CHAR_REFS` 约束，多出的照样被挤掉并逐张点名）。
- **`tag`（自由文本，人读）**：方案或用户给的显示名——"无面部白模三视图"、"6 肖像"、"服装局部特写×3"。只用于详情页/命名屏的**标签**，**绝不进** `allocateRefs` 的判断。

`CardView` 变为 `{ url, kind, role?, tag?, note? }`。

> ★★★ **`kind` 必须原样留在线上，且每次都要写**（2026-08-24 核实服务端后的更正，此前本节写的"kind 保留为兼容读"不够）：
> `kind` 是**跨仓冻结的 `z.enum(["face","body","detail"])`**（server `schemas/branchAsset.schemas.js`）。两条硬约束：
> ① **给 kind 加新取值 = 老服务端整批 400** → `emitApiError` 全 app 没人监听 → **静默丢卡**；
> ② **`z.object` 默认 strip 未声明字段** → 只在 app 侧加 `role`/`tag` 而不动服务端，表现是"客户端发了、服务端 201 了、读回来是空的，全程零报错"（`deck` / `modelUrl` / `views` 都这么丢过）。
> ⇒ 所以：**`kind` 一个取值都不加**，它继续当"给存储层和老客户端看的那一份"；`role`/`tag` 是**新增的可选字段**，要按 CLAUDE.md 那条坑**五处一起改**（server 的 `schemas/branchAsset.schemas.js`、`models/cardView.schema.js`（两个 model 共用的子 schema）、`models/BranchDeck.js` 的 `snapshotCardSchema` 若另有一份、controller 的 `toCardPayload`/`toDeckPayload`、app 的 `api/branch.ts`）。
> ⇒ 写卡时**始终同时写 `kind`**（由 `role` 反推的最佳近似），这样老服务端/老客户端拿到的仍是完全合法的三值数据，只是丢了 tag 的花名 —— **降级而不是损坏**。

**`role` ↔ `kind` 的映射（必须让老数据行为一个字节都不变）**：

| 老 `kind` | 新 `role` | 分配优先级 | 说明 |
|---|---|---|---|
| `face` | `face` | 0 | 锁脸 |
| `body` | `primary` | 1 | 锁主体/服装，也是卡面 |
| `detail` | `aux` | 2 | 进模型的补充参考（非人物卡第二轮真的会取它） |
| —— | `display` | ∞ | **新增**：明确只展示、永不进模型（方案里的"原片截图"、"6 肖像"里排不上的那些） |

`ROLE_ORDER = {face:0, primary:1, aux:2, display:∞}` 逐位替换今天的 `KIND_ORDER = {face:0,body:1,detail:2}` ⇒ **老卡的分配结果完全不变**（人物卡仍 `MAX_CHAR_REFS=2` 只取 face+body、非人物卡第二轮仍取 index 1）。回写 `kind` 时反过来映射（`face→face`、`primary→body`、`aux|display→detail`）。

> ★ 为什么必须拆：合成一位（"tag 既当显示又当管线键"）的话，用户把一张图 tag 成"细节"、另一档方案又把"细节"当出片用——同一个词在两档里管线行为相反，静默扣错钱。`role` 受控、`tag` 自由，才能既灵活又让"花的钱喂给了谁"只有一处真相。

### A3. `PromptScheme` 实体 + 市场

一套方案 = **N 个图位模板**，每个图位 `{ tag, role, size/aspect, promptTemplate }` + 方案级 `{ id, title, author, cardTypes[], coverExamples[], remoteId? }`。

- **`promptTemplate`**：带占位符的提示词（如实操案例的 `{{角色类型}}`）。占位符=用户自定义 tag 的注入点。**必须硬编码那条"风格跟随参考图、不点名画风"**（`portraitViews` 现有那条实测结论）——方案作者可改构图/图位，但画风跟随源图这条不开放，否则又回到"动漫化真人"那个老坑。（2026-09-04 补：这条句子是**条件句**，由模型判参考图是不是照片；参考图低清/重压缩时它会判错。所以调用方已知是真人时走 `slotPrompt` 的 `realPhoto` 档 —— 无条件锁成真实摄影，见 `promptSchemes.PHOTO_LOCK_CLAUSE`。）
- **市场基建直接复用模板市场那套**（`data/templates.ts` 的 mine/shared、`registerTemplate`、`refreshRemoteTemplate`）。⚠ CLAUDE.md 头号坑照搬：**服务端给 `PromptScheme` 加字段 = 本机那几跳（解析/类型/落库/mine+shared 刷新）四处一起改**，漏一处零报错走上一代逻辑。
- **方案预览图**：作者出一次、存成 `coverExamples`，**不每次重画**（省钱、也让市场加载快）。

### A4. 生成流程：scheme-driven，图位数可变 → 计价可变

- `portraitViews` 从"写死 body+face"改成**遍历方案图位**：每个 slot 跑一次 `genImageAsDataUrl(slot.promptTemplate 注入用户 tag, { imageRefs:[源裁剪], size: slot.size })`，串行（顶档一张可到 70s，并发撞限流）。返回 `CardView[]`（各带 role+tag）。
- **计价必须随图位数走**，不再写死 `2×ONE_IMAGE`：`schemeCost(scheme) = 生成型图位数 × ONE_IMAGE`。**报价=实扣**（铁律 + `payOrder.spec` 精神）：命名屏按钮上的数、`canAfford` 的门、`spendTokens` 的实扣，三处读**同一个** `schemeCost`。`display` 型图位若是"原片裁剪降级保留"（不调模型）就不计费——与现有 detail 位同一处理。
- 失败逐张点名、不动已成的图与原裁剪（铁律八，照 `makePortraits` 现有 try/catch）。

### A5. 灵活展示

- `CardDetailPage` 的 `CardViewsSection`：图位标题从 `slotLabel(type, kind)` 改成读 `view.tag`；「出片用 / 仅展示」徽标仍从 `refUsedFlags`（现在按 `role`）取——**判据一处不变**。
- 命名屏（`VideoCardAnnotator`）：把"AI 生成干净立绘"那颗按钮换成**选方案**（下拉/横滑卡片，带 `coverExamples` 缩略），选完按 `schemeCost` 报价、生成。撤销/「↺ 用回原片」保留。
- `CARD_SLOTS` 退化为**兜底方案**：没选方案（或老卡）时的默认三格/两格，仍从这里来。

### A6. 迁移（零迁移，判否定）

- 老卡 `views[].kind` → 读时归一：`face→{role:"face",tag:"面部特写"}`、`body→{role:"primary",tag:slotLabel}`、`detail→{role:"display",tag:"标志性细节"}`。**在 `viewsOf` 一处做**（全仓唯一归一处）。
- 缺 `scheme` = 老卡/老流程 = 走 `CARD_SLOTS` 兜底。判**存在性/否定**，不拿新字段做等值判（CLAUDE.md「后加字段判否定」那条）。

### A7. 可行性结论

**高。** 这是 A（模板市场基建）× B（`portraitViews` 现成生成流）两套已有系统的合流。真正的活是 **`kind`→`role`+`tag` 的拆分**（碰 `viewsOf`/`allocateRefs`/`refUsedFlags`/详情页四处，但每处都只改"读哪个字段"）+ **scheme-driven 计价**。风险点就一个：`role` 词表定完别再动，`allocateRefs` 的语义全压在它上。

## B. 「大概率绕过真人限制 + 多次尝试 + 举报免责」——不做

用户的设想：市场里放一些"大概率绕过 Seedance 真人检测"的方案，让用户在 app 上**反复抽卡**直到某次蒙混过关；理由是"官方没做规避机制、是用户自行尝试"，再配一个视频举报下架功能当合规姿态。

**把它当合规方案来评估，它不成立**——它甩不掉责任，反而把责任攥得更紧。逐条：

**B1. 供应商归因：封的是你的 key，不是用户。** 每一次 Seedance 调用都挂在 **app 自己的方舟 API key** 上。方舟看到的是"这个账号在反复冲真人过滤器"，它按账号封号，`用户自行尝试`这层它根本看不见。而"多次尝试直到蒙过"制造的正是**反复的擦边请求**——这是滥用检测最标准的触发特征。key 一封，你**整条出片链路**（不止真人卡，所有档）当场全死。这一条是决定性的。

**B2. 策展 = facilitation，deniability 是假的。** 一个普通自由输入框（你现在的 requirement 框、canvas agent 都是）确实是中立工具，用户本就能敲任何字。但**市场**是另一回事：平台**收录、排序、用示例图展示"这套方案成功做出了真人卡"、把"绕过率高"的往前推**——这不是"我们没做机制"，**这套策展本身就是那个机制**。中立管道与主动帮凶的区别就在这。所以 §A 的市场有一条硬规则：**不得按"绕过率"排序/标注，预览示例不得是真人**（用原创/二次元/无脸主体演示），否则 A 自己滑进 B。

**B3. 举报是反方向的下游控制，还坐实"明知故犯"。** 举报下架管的是**已发布**成片，而非自愿真人 deepfake 的伤害在**生成/下载那一刻**就已造成，下架删不掉已流出的那份。更糟：一边开着"绕过率方案市场"、一边拿举报按钮当合规招牌，这正是"明知并提供工具"的证据形态，加重而非减轻责任。

**B4. 肖像权/深度合成规定落在运营方，且和你刚上线的 AIGC 标识自相矛盾。** 若成片是可辨认真人又无本人授权，作为提供工具并留存成片的平台，你比终端用户更在追责链上。你这版**才刚**加「AI 生成」角标去合规同一部法规，转头做一套规避真人授权的机制，方向是拧的。用户勾协议只分摊了**你与用户之间**的肖像权，它管不了 **B1 你与方舟之间**的违约。

**B5. 纯产品层面"多次抽卡"也是坑。** 每次尝试都是一发付费视频调用，"抽到蒙过为止"= 用户为失败反复付钱 → "我抽了 5 次全失败"的差评与退款纠纷。就算合规也是钱与口碑的双漏斗。

**B6. 它毒化 A。** A 本身对正当用途（二次元、原创角色、写实→虚构、以及**思路2 那种无脸白模**）就足够有价值，不需要 B 来撑。把 B 焊上去，A 就会招来 B1 那种封 key 流量，把好功能一起搞死。

### LibTV 调研更正（2026-08-24）：它不是"绕过"，是官方合规渠道

平台评论区盛传"LibTV 绕过了 Seedance 真人限制"。**查下来这个前提是错的**：

- **LibTV = LiblibAI 的多模型聚合画布**（接了可灵/Wan/Seedance/Hailuo/Vidu/Pixverse），云端画布 + 可选本地部署。它对 Seedance 真人的处理**不是绕过，是把字节的官方合规流程搬进了自己 UI**：
  - **真人形象**：右键图片→「Seedance 2.0 合规校验」→系统生成**专属二维码**→**被生成者本人手机扫码**→完成**活体人脸识别 + 肖像授权确认**→照片须与活体验证人一致（过度美颜不给过）。**这就是方舟官方 `asset://` 肖像授权那条路**的产品化。
  - **AI 形象**：上传 AI 生成的脸→合规校验判定**不是真人**→放行。（有的实测文只看到这一路，就以为"校验=挡真人"，其实真人是另一条带授权的路。）
  - LibTV 便宜（0.35 元/秒 vs 即梦 1 元/秒）是**批发转售**，不是破解。所谓"真人模式解禁"指的是**带授权门的合规回归**，不是拆了过滤器。
- **字节官方口径**（财联社引抖音副总裁李亮）：**需真人认证才能做本人数字分身，暂不支持真人人脸参考与 IP 形象生成**，团队投入最多的就是反侵权。⇒ 官方合规只有两条：① **活体认证→本人数字分身**（认证后该分身出片不再触发人脸审核）；② **先转成"像你"的虚拟形象再用**（= 我们的白模/无脸方案哲学）。
- 评论区那些人实际在做的分四类：① LibTV 合规真人模式（扫码授权，正当）；② AI 形象（没有真人，正当）；③ **融图/首尾帧/2.0-mini 的灰色技巧**——那是**画面无缝**的剪辑技巧 + 钻"首尾帧不算主体参考"的范围空子，**不稳定（抽卡）、且在收口**，与 LibTV 的合规渠道是两回事；④ 本地跑开源 Wan（无云端过滤器，但要 GPU）。"如果用画布配置都不刚需"这句确认了多数人用的是**云端 = 那条持牌渠道**。
- 网上确有"100% 过人脸 14 种方法"这类**真·绕过指南**——但那正是 §B 说的死路：把这些系统化进 app，等于拿**你自己的方舟 key** 去反复冲人脸过滤器，封的是你整条链路。

**对本方案的净影响**：真人卡的合规产品路更清楚了 = **做一个"被拍者扫码活体授权"的流程**（LibTV/方舟都是这么做的），而不是 §B 的规避。这条可以进 §A 的市场作为"真人档专用前置步"，与现有 MiniMax 真人档、白模/无脸方案三条并列。是否接方舟 2.0 `asset://` 授权见下方待办附录（若要我调研可加）。

**来源可信度提示**：LibTV「0.35 元/秒解禁」多为带货式 SEO 文，但**扫码活体授权这套机制**在多个独立来源一致、且与方舟官方（火山方舟控制台人脸核验+肖像授权）和财联社引李亮的表态吻合，可信；"解禁/不排队"的营销措辞不必当真。
