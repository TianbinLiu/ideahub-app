## 1. 尺度诊断：桌子为什么大了（SCALE 3.2 → 1.0）

**病根不是桌子，是尺度基准。** 上一版为了让 22×9 的 PBR 盖板把 splat 里的桌面整个盖住，
把房间放大了 **SCALE = 3.2**：量出来纵深 7.96 m 的屋子变成 25.5 世界单位、桌面 2.5 m 变成 8.0、
桌高 0.765 m 变成 2.45 —— 而铸卡师（TripoNpc，真人比例 **1.7 世界单位**，她没跟着放大）还是 1.7。
结果上一版验收图里她像个 1/10 的手办站在一张平台上：

| 比值 | 上一版（SCALE 3.2） | 真实/本版（SCALE 1） |
|---|---|---|
| 桌长 ÷ NPC 身高 | 8.00 ÷ 1.7 = **4.71** | 2.50 ÷ 1.7 = **1.47** |
| 桌高 ÷ NPC 身高 | 2.45 ÷ 1.7 = **1.44**（比人还高） | 0.765 ÷ 1.7 = **0.45**（≈ 腰） |
| 房深 ÷ 桌长 | 25.5 ÷ 8.0 = 3.18 | 7.96 ÷ 2.5 = **3.18**（同一间屋，比例不变） |
| 房深 ÷ NPC 身高 | 25.5 ÷ 1.7 = **15.0** | 7.96 ÷ 1.7 = **4.68** |
| 桌宽 ÷ NPC 身高 | 3.74 ÷ 1.7 = 2.20 | 1.17 ÷ 1.7 = **0.69** |

**改法**：以房间为基准 —— splat 点云量出来的 **7.96（纵深）× 4.31（宽）× 3.84（高）就是米**，
于是 `SCALE = 1.0`。四个数（桌长 2.50、桌宽 1.17、桌高 0.765、房深 7.96）与 NPC 的 1.7
摆在一起，上面那张"真实"列就是验据。**"桌子在画面里占多大"改由相机位置调，不再动场景缩放。**

### 1.1 新的落位四件套（`gsStep0.ts`）

```ts
const YAW_DEG = 20.15;  // 不变：窗在 -z、壁炉墙在 -x
const TILT_DEG = 0;     // 上一版 -6°；这一版必须 0（否则网格桌面与 splat 桌面上下错开 2.5·sin6° ≈ 0.26 m）
const ROLL_DEG = 1.203; // 新增：点云桌面法线对 +y 歪 1.2°（房间的 s 轴方向），不纠远端会高出 5.2 cm
const SCALE = 1;
const TARGET = [0, -0.02, 0]; // 桌面顶面中心；y=-0.02 让 splat 桌面沉到网格毡面（+0.004）下 2.4 cm
```

- **ROLL 是量出来的，不是凑对称**：桌面那层点云的法线 = (-0.0212, 0.9998, 0.0005)（yaw 之后的世界系），
  对 +y 歪 **1.22°**；2.5 m 长的桌面远端因此比近端高 5.2 cm —— 不纠的话网格毡面压不住 splat 桌面，
  验收图里"桌面远半截变成 splat 的灰桌面"就是这么来的（本日志 §6 的第一版截图）。
  纠完残差 std **0.94 cm**，网格毡面再抬高 2.4 cm 就盖住了。
  代价：整间屋绕视线轴侧倾 1.2°（窗心横移 ~12 cm），肉眼看不出来。
- **TARGET.y = -0.02**：splat 桌面顶面中心落到 -0.02，网格毡面顶面 +0.004 → 网格比 splat 高 2.4 cm。
  桌高相对地板（splat 地板在 -0.785）= **0.789 m**（毡面顶 0.004 到地板），比量测的 0.765 多 2.4 cm ——
  这是"盖住 splat 桌面"的代价，仍在 NPC 腰部。
- **删了 tilt 之后圆窗还在画面里**：米制机位俯角 ~27°、窗心只比桌面高 0.68 m、在相机前 ~5 m
  ⇒ 窗心在视野轴上方 ~15°，50° 垂直视野装得下（见 §5 的俯视截图）。

### 1.2 新机位 `layout.GS_CAM`

```ts
GS_CAM = { pos: [0.55, 1.1, 2.0], look: [-0.1, 0.0, -0.9] };  // 俯角 ≈ 20.8°，距桌心 ≈ 2.35 m
```

- 老 `LAND_CAM` 是 (0, 3.9, 7.4) / 俯角 30° —— 对 22×9 的"UI 画布桌面"合适，对 2.5×1.17 的真桌子
  就是"站在三米外俯拍一张课桌"。新机位的选取顺序（都按 800×363 的 app 画幅量）：
  1. 先按"桌面要占画面下半"定机位高度/距离：**pos y 1.1、z 2.0（桌心后方 2.0 m）**；
  2. 再看 NPC：她站在 z=-1.9，1.75 m 高，头顶落在画面 **~12%**（顶部 UI 条以下）；
  3. 再看窗：窗心落在画面 **右上 20~30%**，不被 NPC 完全挡住（截图里她站在窗前偏左一点）；
  4. 俯角 21° 比老机位 30° 浅一档（真桌子只有 1.17 m 深，30° 会把桌面压成一条）；
     桌面近边落在画面下缘外（与老场景一样"桌子从画面下缘伸出去"）。
- 相机只影响构图，**不改场景尺度** —— 这一条写死在 `defaultCamFor`：GS 米制档只返回 `GS_CAM`。

### 1.3 桌面与 splat 桌子的对位

- **同向同寸**：splat 那张长桌长轴沿房间纵深 d（世界 z），2.50 × 1.17；网格桌面也是 2.50（z）× 1.17（x）。
  上一版是把 22×9 的横向盖板压上去的（方向都不同，只是靠尺寸大盖住）。
- 网格桌面的顶面（毡面 +0.004）把 splat 桌面（-0.02）整块盖住；点云 ±0.94 cm 的残差尾巴
  **理论上会零星透出**，验收三张里没有可见的穿透（见 §8 风险 1）。
- 桌面**不落地**的老观感只在老场景保留（GS 关着时桌腿沿用旧高度）；米制档桌腿落到地板 -0.785。

## 2. 旧桌面是怎么找回并复用的

1. **源头**：`TableScene.tsx` 在 GS 第 0 步之前那一版（commit `e225b5e9^`，G4 时期的"赌桌绒呢桌布 + 皮革软包护栏"）
   里的 `makeFeltCloth / TableCloth / TableRail / Table / CenterLine`。
2. **搬出来**：整段几何与材质**原样**搬进新文件 `WorkshopTable.tsx`（视觉参数一个没改）：
   深绿毡面（`#123c2a` + 噪点）、金色印花（双重边框 / 庄家弧线 / 中央法阵 24 射线 / 四角菱花）、
   黄铜色皮革软包护栏（圆柱 + 四角圆球）、深胡桃木桌体/桌沿/桌腿、青色中线。
3. **参数化**：组件接 `T`（桌面尺寸）+ `height`（离地高）+ `metric`（米制装饰档）。
   - 老场景：`T` 来自 `layout.sceneLayout(land).table`（横屏 22×9 / 竖屏 16×7），`metric=false` ——
     尺寸、护栏半径 0.17、桌沿 0.6 宽、桌腿 0.4 → **观感逐字节不变**；
   - 米制档：`T = GS_TABLE (1.17×2.5×0.14)`、`height=0.765`、`metric=true` —— 护栏半径 0.035、
     桌沿 0.03、桌腿 0.06 且落到地板、毡面 0.97×2.35、四角菱花去掉（1.7 cm 的角花会糊成噪点）。
4. **删掉盖板**：`GsStep0Environment.tsx` 里的 `GsTableCover` 与它的木纹/法线生成函数（约 120 行）整个删了；
   `TableScene` 现在只有一处 `<Table />`，它再调 `<WorkshopTable>`。这样"桌面尺寸"只剩一处（layout），
   不会出现"桌子和盖板各画一半"。
5. **材质**：米制档从 `meshStandardMaterial` 换成 **`meshPhysicalMaterial`**，`roughness=0.78`、
   `metalness=0`、`specularIntensity=0.18`、`envMapIntensity=0.06` —— 毡面保持哑光，
   且**掠射角下不再出现"桌面右半截发灰的冷镜面"**（第一版验收图里的那层灰就是标准材质 4% F0 的
   Fresnel + PMREM 冷天空；任务要求"别出现镜面反光"）。

## 3. 桌面光毯（lightmap）

### 3.1 怎么生成

`design/gen-table-lightmap.mjs`（**零依赖**：只用 Node 内置 `zlib`，自写 PNG 编码；不需要 canvas/sharp）：

```bash
node design/gen-table-lightmap.mjs                     # 写 public/models/study/tex/table-lightmap.png
node design/gen-table-lightmap.mjs --window 0.7 --fire 0.8 --sigil 0.5   # 调三种光的强度
node design/gen-table-lightmap.mjs --seed 7 --out /tmp/x.png             # 换噪点种子 / 换输出
```

- 尺寸 **1024 × 512**（RGBA8；长轴 = 桌面 2.5 m 方向，一张 texel ≈ 2.4 mm），与桌面长宽比（2.14）匹配。
- 三种光（参数都在脚本顶的 `PARAMS`，可调）：

| 光 | 参数 | 读数（0~255） |
|---|---|---|
| ① 圆窗冷光斑 | center (u .76, v .52)，椭圆半径 (.20, .34)，色 (0.62,0.76,1.0)，strength **0.5** | 池心 **155,160,195** |
| ② 左前壁炉暖光 | center (u 1.04, v -0.10)（远端左角之外），半径 (.78,.95)，色 (1.0,0.44,0.16)，strength **0.6** | 远端左角 **164,81,43** |
| ③ 中央法阵自发光 | 与毡面金线同轴，半径 0.0857 m（= 毡面纹理 150/2048 × 桌宽），strength **0.62** | 桌面中心 **72,58,42** |
| 环境 | farCool 0.06 / nearDark 0.14 | 近端右角 0,0,0 |

- 方向约定（与渲染端必须一致）：canvas **x 0 = 玩家这一端，x 1023 = 圆窗那一端**；
  **y 0 = 桌左（壁炉侧），y 511 = 桌右（书柜侧）**。推导见 `WorkshopTable.Lightmap` 的注释
  （贴图 flipY + 父组绕 y 转 90°）。
- 抖动：每像素 ±1.2/255 的确定噪点（同一 seed 每次同一张），压住 8 bit 渐变的带状。

### 3.2 怎么贴在桌上

- `WorkshopTable` 在毡面上再叠一层 **加色平面**（`planeGeometry [2.3, 0.97]`，绕 y 转 90°，
  `blending: AdditiveBlending`、`depthWrite: false`、`toneMapped: false`），只负责"加光"，
  不盖住毡面的金线与法阵（与"当 map 盖上去"相比保留了毡面的 normal/roughness 贴图）。
- 桌面本体仍是**哑光**：roughness 0.78（要求区间 0.6~0.8）、metalness 0、specularIntensity 0.18。
- 贴图缺失不会让桌子消失：加载失败只在 console 说一句，桌面退回纯毡面（光毯是增强项）。
- PNG 体积 **≈ 0.69 MiB**（1024×512 RGBA + 抖动）；要更小可改 RGB / 降噪，脚本里一处就能改。

## 4. 火与光（方案 A 的核心）

### 4.1 壁炉位置：从"估的点"微调到"看得见的炉膛"

- 上一版 `ANCHOR.fire = (s -3.18, d 4.80, y 0.50)` 是**估的**（炉膛被家具挡住，量不到）。
  米制场景里把火放在那里，验收图里火焰**悬在壁炉右侧的墙上**（截图 `.tmp-gs-table/` 的第一轮）。
- 本版按"允许微调到视觉合理处"移到 **`(s -2.72, d 3.10, y 0.62)`** → 世界 ≈ **(-1.45, -0.24, +0.10)**：
  正对壁炉开口、离桌面左沿 0.87 m、离 NPC 左肩 ~1.9 m。位置仍由 `toSplat/toWorld` 现算，**只改一处**。

### 4.2 三件东西（`HearthFire.tsx`）

1. **点光源**：暖色 `#ff9a4a`、`intensity 7` / `distance 5.5` / `decay 2`（米制 1/d² 衰减）。
   闪烁 = 7.3 Hz 主频 + 2.1 Hz 呼吸 + 23.7 Hz 细抖的**多频正弦叠加**（幅度 22%，不是随机跳变——
   随机跳在低帧率下读成"坏灯"）；炉心位置 ±2.5 cm 轻跳。
2. **火焰动画**：`ShaderMaterial` + 5 层 fbm 噪声（向上卷动 + 低频左右摆），泪滴轮廓 × 噪声阈值，
   颜色从底部暗红 → 橙 → 顶上黄白；**双层**（外焰 0.38×0.55 m + 内焰 0.55 倍）、加色混合、
   绕 y 轴面向相机（只转 y，转 x 会像烧到桌面上）。
3. **假光池**：炉前地面一块 1.5×1.1 m 加色渐变（splat 地板不吃灯 —— 不加这一块，火"照不亮任何东西"），
   炉口再叠一层 2.6 倍大的柔光晕。`renderOrder={20}` 是整个火能看见的前提（见 4.3）。

### 4.3 ★ 光照边界（注释里写死，别以后以为火对墙也生效）

- **light 只照 mesh**：splat 用的是 ShaderMaterial，three 只给"要灯"的材质上传灯光 uniform。
  所以这盏点光只照到 **桌子 / NPC / 卡牌 / 法阵**；**splat 的墙、窗、地板一个像素都不会变亮**。
  "墙也暖一点"不要靠调灯（只会把桌子和人烤过曝），桌面暖靠光毯、地面暖靠假光池。
- **火必须画在 splat 之后**：SparkRenderer 是**透明**材质、`renderOrder=10`；火焰默认 0 会先画，
  然后整片 splat 糊上来。第一轮验收"壁炉里看不见火"就是这个原因（不是位置错、也不是 shader 没跑）。
  火焰 / 内焰 / 炉口光晕 / 地面光池四个网格全部 `renderOrder={20}`（与 `GsStep0Room` 文件头的
  渲染顺序约定一致：网格 0 / splat 10 / 玻璃与光效 20）。

### 4.4 灯组其余部分（米制重调）

| 灯 | 上一版（SCALE 3.2） | 本版（米制） | 为什么 |
|---|---|---|---|
| 月光方向光 | `sun [-2.5,7,-12] / 1.5` | `sun [-1.2,3.2,-6] / 0.9` | 方向光强度与距离无关，但桌面离窗近了 3 倍；0.9 是对着 splat 墙面亮度校的（再高桌面比 splat 亮，接缝显形） |
| 阴影框 | ±13.5 / ±9.5 | ±2.4 / ±1.8，near 0.1 / far 12 | 桌面+人只占 ±2 m；同样 2048² 阴影图每米多 6 倍像素（窗棂影从"糊"变"看得出格子"） |
| 窗面泛光 RectAreaLight | 3×3 / intensity 4 | 0.9×0.9 / intensity 12 | 面积小 11 倍、离得近；按现场观感校（第一版 26 把桌面远半截打爆） |
| NPC 补光 | `[0.8,2.6,7.6] / 0.9` | `[0.4,1.6,3.6] / 0.9` | 方向不变（相机侧顺光），距离按米制收；`?nofill=1` A/B 仍可用 |
| 雾 | [20,70] | [7,22] | 房间纵深 7.96 m；窗前 7 m 不吃雾（否则圆窗被雾压灰） |

## 5. 相机与卡位联动

- **卡牌基尺寸只有一个出处**：`layout.cardLayout()` —— 老场景 1.1×1.65，米制档 **0.28×0.42**。
  `CardMesh / SlotPlate / DeckStack / DeckSpread / MarketFan / DragLayer / FlightCard / DialogTableCards`
  全部读它（写死任何一处都会出现"画的是小米制、落点算的是老尺寸"）。
- **为什么是 0.28**：4 张角色卡一排横跨 4·0.28 + 3·0.015 = **1.165 m ≈ 桌宽 1.17**；
  在 800×363 的真机画幅上每张约 **68×28 px**（与老场景 64×34 同一档），卡面放得下封面 + 卡名，
  也不会"卡比桌子还宽"。0.42 深 = 1.5 倍宽（塔罗牌比例）。
- **5 个卡位 = 桌面上分层**（从 NPC 侧到玩家侧，各层卡深相加不重叠）：

| 层 | 世界坐标 | 尺寸 | 屏幕（852×348 投影算，与截图一致） |
|---|---|---|---|
| 场景位 | (0, **-1.0**) | 0.224×0.336（0.8 档） | y ≈ **48%**（远端、法阵之前） |
| 4 角色位 | x = ±0.4425 / ±0.1475，**z=-0.35** | 0.28×0.42（1.0 档） | y ≈ **57%**、x 33~67% |
| 市场两排 | z = **0.15 / 0.50**，dx 0.27，0.72 档 | 0.202×0.302 | y ≈ 67% / 77% |
| 卡组堆 / 摊开 / 合成法阵 | z ≈ 0.92~1.0（玩家这一侧） | 法阵缩到 0.32 | y ≈ 95~100%（贴画面下缘） |

- **"投影法重算"的落地**：旧的 `TABLE_SLOTS` 是按 22×9 桌面的屏幕百分比量的（角色排 y 44~53.5%），
  米制桌面**长轴换成了 z**，那组比例直接套会算到桌面外。本版改用"桌面分层 + 投影校核"：
  先按卡深排层（上表），再把每格投影回屏幕核对（`GameTableSlots` 每帧写 `SLOT_SCREEN`，
  2D 落点判定读同一份）—— 屏幕读数与上表一致，四张卡都在桌沿以内。
- **对话机位**：`layout.npcCam()` 给米制档一台新的 `GS_NPC_CAM = (0,0.72,1.15) → (0,0.35,-1.55)`
  （老场景的 `NPC_CAM` 是世界 UI 尺度，米制下会落到桌子底下）。`studioStore` 进对话、`TripoNpc`
  的注视基准都改成 `npcCam()`。
- **NPC 站位与身高**：新配置 `GS_MILLTINA_CFG`（`TableScene`）。★ 验收探针量出来一件事：
  `MILLTINA_CFG.scale=3.35` 换算到世界是 **约 3.43 m 高**（模型原点→头骨 1.0236 模型单位 × 3.35），

## 8. 已知风险 / 下一步

1. **splat 桌面残差**：ROLL 纠完残差 std 0.94 cm，网格毡面抬高 2.4 cm；>2.4 cm 的尾部点理论上会
   从毡面透出来。三张验收图里没看到可见穿透，但换资产/重估位姿要重量一次。
2. **对话俯身的幅度没重标定**：`GS_MILLTINA_CFG` 只改了站位与胸物理 rail；`leanSlide`
   （back 0.42 / z 0.08 / y 0.216）还是按老桌沿（4.3 m 远）量的。站姿验收图没问题，
   进对话让她伏桌时要再看一次（这是这一版**唯一没动的旧参数**）。
3. **帧率只有模拟器读数**（宿主机 GPU，ANGLE 桌面显卡），真机帧率仍没量；2M 高斯在手机上要按
   设置页两档 + 角标量。
4. **splat 里的椅子**：近侧/远侧各一把烘死在房间里。NPC 站在远端（椅子在她左边），近侧那把在
   桌面右侧当"前景"，三张图里都读得过去；但玩家绕到桌子另一边看会穿帮。
5. **老场景不受影响**：`sceneLayout()` 在 GS 关着时逐字节返回老布局；桌面组件换了实现但尺寸/材质/机位/
   卡位一个数没动（`WorkshopTable` 的 `metric=false` 分支就是原实现）。GS 失败回退时 `setGsPhase("failed")`
   会把米制标志位翻回 false，桌子/机位/NPC 一起退回老场景。
6. **光毯体积** 0.69 MiB（可改 RGB / 降噪）；**GS 资产**（31 + 8 MiB spz）仍不进仓库。
7. **`gsSceneCam` 是验收钩子**：不写这个 localStorage 键就不存在；生产里没人写 = 完全走 `GS_CAM`。
8. **2.5D / Blender 方向没做**（主人拍板先做 A；2.5D 那套仍在 `app` 工作区未提交，不属于本分支）。

1. **两排是平放不是立牌**：立牌会把中线整条挡住（10.4 末尾那段实测），所以"脸对脸"的读感靠

### 11.2 火：三层 + 柴木发光 + 火星 + 火光变色（`HearthFire.tsx`）

上一版是一层 fbm 噪声 + 一个压扁的内焰（§10.6）。这一版按真实壁炉拆成四件：

**① 三层火焰**（同一张 shader、三组 uniform，`FLAME_LAYERS`）：

| 层 | 相对宽/高 | 上卷速度 | 噪声频率 | 湍流 | alpha | 颜色（底→中→顶） |
|---|---|---|---|---|---|---|
| 外焰 | 1.00 / 1.00 | 0.85 | 2.3 | 1.05 | 0.62 | `#5c1103`→`#ff4d0e`→`#ff9b34` |
| 中焰 | 0.72 / 0.80 | 1.45 | 3.6 | 1.30 | 0.68 | `#9c2406`→`#ff7a14`→`#ffc866` |
| 内焰 | 0.34 / 0.50 | 2.30 | 5.4 | 1.55 | 0.75 | `#ff8a1e`→`#ffd485`→`#fff3d2` |

- **顶部飘动更快**是 shader 里的 `phase = uTime * speed * (1 + 1.8·y²)`：相位随高度加速（真火的
  尖端正本来比根部抖得快），横向摆幅也乘 `y²`（根部钉死、尖端大幅摇曳）。
- **轮廓 = 三条火舌取并集**（`for i in 0..2`，每条的水平位/半宽/高度上限由 `uSeed` 定，帧间不变）。
  一条整片的 teardrop 无论怎么加噪声都读作"一团光"；三条不同高低的舌叠起来才有壁炉的样子。
- **颜色是"底部白热 → 中段橙 → 顶端暗红"**（柴火温度最高的是燃料那一段，火舌尖端先冷却）。
  第一版把它写反了（顶部最白），配合加色混合直接烧成一团白 —— 这是这一节踩得最深的一坑。

**② 柴木发光 + 炭化黑边**（`LOGS` 三根交叉的圆柱 + 专用 shader）：
沿长度的发光是 `pow(along, 1.6)`（接触火焰的中段最亮、两端暗）、朝上的面再压 `1−0.85·up`
（"底部亮、顶部暗"），炭化是"两端 + 上表面"进一段近黑 `#050303`，交界处留一圈暗红余温。
柴木**压在锚点下方**（锚点 = 柴堆上表面，最上面那根的中心 = −0.5·半径），吃深度、进不透明队列。

**③ 火星/余烬**：32 颗 `THREE.Points`，位置/寿命/大小全由 shader 从 `aSeed` 现算（CPU 每帧只写
一个 uTime）：寿命 1.2~3.1 s、向上飘 0.04~0.34 m、左右轻微飘移、头尾淡入淡出。
> ⚠ **这一版最贵的一个坑**：`gl_PointSize` 第一版给到 42~58 —— 那是"视距 1 m 处的**物理**像素"，
> 除以视距之后每颗 200+ px，32 颗软点叠在一起就是**一个白色椭圆**。验收第一轮看到的"过曝的火"
> 其实是它们，不是火焰。改成 7 之后火星才是火星（顺带：那团白色消失之后，火焰的层次才看得见）。

**④ 火光闪烁**：点光强度沿用多频正弦叠加（7.3 / 2.1 / 23.7 Hz，幅度 22%），这一版**颜色跟着强度走**：
`#ff7a2f`（暗）↔ `#ffb066`（亮）线性插值 —— 真实火焰变暗时色温同时下降。

**包围盒（运行期读 `window.__gsAccept.fire`）**：锚点 (−1.949, −0.500, +0.101)，
`x ∈ [−1.999, −1.899]`（柴木厚度）、`y ∈ [−0.630, −0.080]`（柴底 → 火舌顶）、
`z ∈ [−0.049, +0.251]`（外焰 0.30 宽的一半）。炉口内净高 ≈0.55 / 宽 ≈0.60 ⇒ **整团火收在炉膛口内**。

**为什么不用视频贴图**（主人给了 ≤1.5 MB 的口子，我们选纯程序化）：
① 这份火要能随炉膛尺寸/相机距离缩放，而循环贴图分辨率定死（近景要 ~300 px、远景只要 ~40 px）；
② 无缝循环的火焰视频要么买素材、要么离线渲染 —— 仓库里没有可用素材，也不该为一个壁炉角落
   进 1.5 MB 纹理解码预算；③ 程序化的三层 + 火星**天然无缝**（相位永不重置），视频每 N 秒会重播。

### 11.3 人物居中（z +0.50 → −0.03）

- **屏幕右 = 世界 −z**（相机在 +x 看 −x，相机的右手方向 ≈ −z），所以"往右挪"就是 **z 减小**。
  上一版站 z=+0.50，投影出来正好**偏左 0.52 m** —— 就是主人说的"位置偏左"。
- 量法（`window.__gsAccept`）：把她 **hips 骨的世界坐标**与**桌心 (0,0,0)** 各沿"相机右手方向"
  取分量，两者之差就是画面上左右方向折回世界坐标的米数（NDC 是分量除一个与深度成比例的尺度，
  两边乘回来正好约掉，所以这个数就是"在她那个深度上量到的米"，与画幅无关）。
- **读数**：`npcCenter = [−0.790, 0.107, −0.03]`、**`npcOffsetM = 0.012`**（≤ 0.1 ✓）。
  这条式子容许的区间是 z ∈ [−0.13, +0.07]，取 −0.03 是中点：**炉膛在 z≈+0.10**，
  再往 +z 挪让火从她身侧露出来就会重新偏左。
- ⚠ 代价：她站到炉口正前方之后，**正面机位只剩她两侧的缝隙看得到火**（截图 1 里火从她左手边
  露出来一条）。火的三层/火星要在**壁炉近景**（截图 3）里看。

### 11.4 椅子：用 `SplatEdit` 把点云里的椅子裁掉（`GsSplatCull.tsx`）

那把高背雕花椅是**点云里烘死的几何**：没有对象可删、没有材质可关，`SplatMesh` 的 visible
是整块房间的开关。**盖 mesh / 调近裁剪都不行**（会连地板和桌角一起切掉，而且换个机位就穿帮）。
最后用的是 Spark 2.4 自带的编辑通道：

- `SplatEdit({ rgbaBlendMode: "multiply" })` + 若干 `SplatEditSdf({ type: "box", opacity: 0 })`；
  着色器对每个高斯算一次"在不在盒子里"，在的话把它的 rgba **乘** 上 (1,1,1,0) ⇒ alpha 0 ⇒ 不画。
  `softEdge: 0.012` 给盒子边界 1.2 cm 的软过渡（硬切会在边上留半颗高斯的亮边）。
- 组件挂在**场景根**上（不是 SplatMesh 子节点）：`SparkRenderer` 每帧把"祖先里没有 SplatMesh"的
  `SplatEdit` 当**全局编辑**收走，于是盒子直接写**世界坐标**，不用反推 splat 那份落位变换。
- ⚠ 盒子**底不贴地板**（y 下限 −0.72）：留下地板那一片点云，否则椅子底下会出现一块"点云被挖掉"的黑洞。

**盒子是怎么量出来的**（不是估的）：把盒子写进 `localStorage.gsCullBoxes` 之后逐轮缩小，判据是
"正面机位那张图里椅背还在不在"（对同一块像素区取与「椅子在」参考图的平均绝对差 >40 = 没了）。
逐轮落点：`z∈[-2.2,-1.0]` 不动 / `z∈[-1.0,-0.6]` 不动 / **`z∈[-0.4,+0.2]` 没了**；
`x∈[-1.3,-1.0]` 不动 / **`x∈[-0.9,-0.6]` 没了**；y 只到 −0.6 不动、抬到 +0.3 就够。
结论：椅子是**塞在桌子远沿**的（椅背贴着桌沿站），最终盒子
`c = (−0.695, −0.16, −0.215)`、`h = (0.105, 0.56, 0.335)` ⇒ x∈[−0.80,−0.59]、y∈[−0.72,+0.40]、z∈[−0.55,+0.12]。
**只有一把**（`z∈[-1.6,-0.7]` 与 `x∈[-1.3,-1.0]` 两轮都没命中任何东西）。

### 12.2 取景右移：为什么最后是「移轴」而不是转头

**目标**：NPC 身体中心 49.5% → **58%~62%**，桌子中线同样右移，且**桌右沿不出画**。

**先试「把 `GS_CAM.look` 点往右挪」（纯转头），量完否掉**（画布 852×348、fov 50）：

| look 点 z | NPC 身体中心 | 桌右沿（木端板 z=−1.25） |
|---|---|---|
| +0.00（原） | 50.61% | 89.14% |
| +0.25 | 56.50% | 98.95% |
| **+0.30** | **57.7%** | **101.2%（出画）** |
| +0.34（把 NPC 推到 60% 需要的量） | ~60% | ~104% |

纯转头是**角度**平移，靠画面右边的桌右沿走得比人物多 —— 主人两条要求在这个做法下**无解**，不是没调好。
「整体 group 平移 x」也不行：网格桌面会跟 splat 里烘死的那张桌子错开（两端就靠 `GS_TABLE.splatLen` 的木端板盖着），
平移 NPC 又会让炉膛的火偏出她身侧；而且单纯平移（不转 look）不改变构图。

**最后用投影窗口右移**：`camera.setViewOffset(W + 2·δ, H, 0, 0, W, H)`，`δ = round(852×0.09) = 77 px`。
只换投影窗口、不改相机位姿/朝向/焦距 ⇒ 桌子在画面里的尺寸与人物高度**逐像素不变**，画面里所有东西一起右移 77 px。

量出来的数（`window.__gsAccept`，模拟器 852×348）：

- NPC 身体中心（hips 投影）**50.61% → 59.65%**；截图上"亮发+绿裙+肤色 → 最大连通块"量到 **59.75%**（差 0.1%，同一处）；
- 桌右沿（z=−1.25 的木端板）**89.14% → 98.18%**（仍在画内，余 1.8%）；桌左沿 11.8% → 20.8%；
- 生成键铭牌 73.8% → 83.2%（还在画内，离右缘约 5% 余量）。

⚠ **只在设计机位上生效**：验收用的 `gsSceneCam` 覆盖、对话/聚焦/商店机位都不移（`syncGsFrameShift` 的条件里那四个判断）；

### 12.3 小幅环视 ±6°/±3°（`scene/gsLook.ts`）

- **手势门**：`TableCatcher` 的 `mode()` 在"米制档 + `camera.kind === "default"` + 无 orbit"时返回 `"gsLook"`；
  老场景仍返回 `null`（`SHOW_PLAYER_BODY=false` + `orbit=null` ⇒ 手势门恒 null —— 这就是主人说的"拖拽完全不生效"）。
- **卡牌/铭牌上按下不进入环视**：按下时对 `scene` 做一次 `Raycaster.intersectObjects(scene.children, true)`，
  逐层看 `object.__r3f.eventCount`（R3F 自己的命中筛选就是它）；`userData.noCam` 的**空白桌面拾取面**跳过。
  卡牌 / 铭牌 / NPC / 卡组 / 场景位都挂着 onClick/onPointerDown ⇒ 按在上面走原路，不进入 gsLook；空白桌面与背景（splat 的 `raycastable: false`）才环视。
- **参数**：横向 0.0014 rad/px（75 px ≈ 6°）、纵向 0.0010 rad/px（52 px ≈ 3°）；**硬停 ±6°/±3°**（夹在 `gsLookDrag` 里，撞住不弹）。
- **回中**：松手 750 ms、ease-out 三次曲线（`1-(1-t)^3`），在 `CameraRig` 的每帧里推进（不另起 rAF；面板盖着停帧时回中也跟着停，关掉后从停下的角度接着回）。
- **实测（emulator-5554，CDP 触摸）**：按住拖到底读数 **yaw 6.000° / pitch 3.000°**；松手后 60 ms 采样在 **717 ms** 读到 `|yaw| < 0.05°`（750 ms 曲线，采样粒度 60 ms + CDP 往返）。
- 与卡牌拖拽：卡上按下根本不进 gsLook 分支；`g.current.moved` 仍照旧累计，拖完的 click 不会误触 `unfocus()`。
- 与"转头"不是一套：`cameraOrbit.eyeLook` 是第一人称（还要驱动角色头骨），这一档只转相机；共用一个模块会把状态搅在一起。

### 12.4 工作流小窗 + 波浪切换（`studio/ui/WorkflowWindow.tsx`）

| 项 | 值 |
|---|---|
| 尺寸 | **66% × 68%**（模拟器 864×360 CSS 上 = **570 × 245**），中心 (60%, 44%) —— 主人要的"屏幕 62%~70%、居中偏右"取中段 |
| 壳 | 圆角 `rounded-2xl` + `ring-white/15` + 阴影；遮罩 `bg-black/45 + backdrop-blur-[2px]`；底边停在 78%，右下角 GS 角标（z-9999）刚好露在小窗下面 |

| 引导 | 小窗里**不自动弹**画布引导（那份说明卡是整屏宽的，在小窗里会横穿到窗外）；顶栏 `?` 仍可手动重看 |

**3D / HUD 在小窗打开时**（主人第 3 条的"不卸载/不空跑"）：

- 3D **从未卸载**（小窗是叠上去的浮层，不是路由切换）；但 `canvasCovered` 让它**停帧**（`frameloop="never"`，与原来全屏画布同一条机制）。
- 实测：小窗开着 1.3 s，`__gsAccept.frames` **delta = 0**（停帧，不空跑）；关掉后 1.3 s **delta = 62**（≈48 fps）。
- HUD 是 `document.body` 上的 DOM 角标（z-9999）—— **一直挂着**，读数冻结在停帧前那一帧；关掉后恢复（45.7 fps）。
- 3D 画面上能看到桌面/人物在遮罩外露出来的部分，所以"底下还有东西"是看得见的。

**★ 联带修的一个既有 bug**（第一次验收才暴露）：停帧 → 恢复后，`TripoNpc` 的 `leanBody/leanArm` 两个 action 会变成
**stopped 但 `time=0 / timeScale=0`**；旧判据 `pinned = ts===0 && !paused && enabled && time<=0.001` 把它当"已钉住"，
于是 mixer 不再写这两条轨道，头骨停在停帧前那一帧 —— 现象是**关掉小窗后铸卡师歪着头/头发盖脸**。
判据补上 `isRunning()` 之后（`TripoNpc` 两处：站姿钉帧 + 头部注视的 `pinnedNow`），恢复时重新 `reset().play()` 钉回站姿。
dev 里 A/B 复现与修复见 `.tmp-accept/`；`window.__tripo.perfActions` 可直接看 action 状态。

### 13.2 选角逻辑与波浪参数（`WorkflowWindow.pickCorner`）

主人给的是「默认右下角；如果生成键在屏幕另一侧（左半边），圆心改用离它最近的角落」。落成三条：

### 13.4 火的新实现

**① 图集怎么生成**（`design/gen-fire-atlas.mjs`，Node 端零依赖 + 一个带 Pillow 的 Python 只负责编 WebP）：

- **64 帧 × 512×512**，按 8×8 拼成 **4096×4096**，有损 WebP **q=96 → 0.27 MB**（门禁 1.5 MB）；
- 三个场：**上升速度场**（中间快、两侧慢，落在每列纵向缩放 `sy`）、**curl noise**（流函数 ψ 的旋度，
  低分辨率网格算完双线性采样）、**温度场**（横向 × 高度衰减 × 归一噪声咬轮廓，阈值成形）；
- 火焰本体 = **三条解析火舌取并集 + 一层连续火床**（只给一条解析轮廓 + 噪声出来的是标准锥体），
  再被 curl 拧、被上流的噪声撕；
- **无缝**是这份脚本最容易做错的一处：每个八度按"一个图块 = 它自己的一个完整周期"取样（`vn(x, wrap1(y-t), P, k)`），
  于是 `t=1` 的坐标刚好平移一整个周期、与 `t=0` 逐像素相同，**不做任何首尾混合**。
  逐帧差分校准：`|frame0-frame1|` = 3.19、`|frame62-frame63|` = 3.23、**`|frame63-frame0|` = 3.13**、
  作为对照 `|frame0-frame32|` = 24.07 —— 首尾那一跳与相邻帧同一量级，就是"接得上"。
  ⚠ 中间踩过两个坑（都留在脚本注释里）：①把噪声表边长当频率（每格 256 个噪声单元 = 一片静态雪花点）；
  ②把每列速度乘进 `-K_UP·t`（非整数周期，t=1 接不上）。
- **图集只存温度**（单通道灰度写进 RGB 三通道同值）：WebP 有损是 YUV 4:2:0，三通道放同一份数据等于让色度恒定、
  细节一点不丢；颜色全部由 shader 现算。

**② shader 层数**：3 层火焰（缩放 1.00 / 0.90 / 1.12、速度 1.0 / 1.45 / 2.05、相位 0 / 0.31 / 0.67、色温偏移 -60 / +30 / +120 K），
每层在**相邻两帧之间交叉淡化** ⇒ 每像素 **6 次图集采样**（`FIRE_FX.atlasTaps`）。一整个循环 5.2 s。

**③ 黑体色温**：`blackbody(K)` 用三段 smoothstep 近似 CIE 黑体轨迹的 sRGB 色（800 K 暗红 / 1400 K 橙 / 1900 K 黄白），
温度 = `900 + 1000·heat^1.2` K；**亮度与色度分开走**（`heat^1.5`），所以芯白、边红、尖暗是同一套映射自然出来的。
**蓝焰根部**：`vUv.y < 0.14` 且"有火但温度还不高"的那一圈掺 0.75 的蓝（化学发光，不在黑体曲线上）——
只出现在根部，不会把火整体染蓝。

**④ 柴木与余烬**：柴木保留第 3 版那条沿长度的 emissive 渐变（中段最亮、朝上的面压一档、两端炭化）；
新增 **16 颗炭火发光点**（`COALS`，贴在柴堆上表面的随机点，2.1~6.7 Hz 各自闪烁，不参与上升）——
与"32 颗往上飘的火星"分开成两套 points。

**⑤ 烟**：**4 片**半透明面片（普通混合，不是加色），每片自己的相位与寿命（2.4~3.5 s），
上升 + 横向漂移 + 越往上越散 + 头尾淡入淡出**全在 shader 里**（CPU 每帧只写一个 `uTime`）。

**⑥ 热扰动**：炉口上方一片 `0.345 × 0.294 m` 的"抖动的热雾"（加色，alpha ≤ 0.075），UV 随 `uTime` 上移。
★ 这是**近似**：真要扭曲背景得先把场景渲进 render target 再采样（postprocessing 那条路），主人点名不要引那个依赖。
观感是"炉口上方的空气在抖"，但它**不会**真的把后面的 splat 墙拧弯（见 13.6 风险 2）。

**⑦ 光**：主点光强度/颜色联动不变（7.3/2.1/23.7 Hz 三频、幅度 22%）；新增一盏**很弱的炉膛内补光**
（`#ff7a34`、0.55 / 距离 1.2 m / decay 2，位置在火后面 0.1 m、高 0.16 m），照柴木的背光面与桌沿。
★ **splat 的炉拱不吃灯**（SparkRenderer 是 ShaderMaterial，three 只给要灯的材质上传灯光 uniform），
所以"炉拱被照亮"靠的是新加的一片 **0.62×0.50 m 的加色光晕**（`arch`，opacity 0.3）压在火焰后面。

  +7 次 draw call / +14 个三角 / 6 次小面积纹理采样，相对场景里 400 万高斯 + 109 次 call 的底子是小数。
  真机 ≥50 fps 这一条**还没在真机上量过**（见风险 1）。

### 13.7 这一版的风险 / 下一步

1. **真机中端机 ≥50 fps 没量过**：模拟器是宿主机 GPU。按 13.5 的预算（+7 call / +14 tri / 21 MB 纹理）
   应该没问题，但"应该"不是读数 —— 下一步找台中端机（骁龙 6 系这个档）实测一次，重点看两个数：
   图集上传那一下的卡顿（4096² WebP 解码 + 缩放，估 150~350 ms，发生在进工坊的那一刻）与开火后的稳态帧率。
2. **热扰动是"热雾"不是真扭曲**：不会把后面的 splat 墙拧弯。要真扭曲必须引 render target（postprocessing），
   这一版按主人要求没引；如果观感上还想要"炉口后面在晃"，那是下一个独立决定。
3. **图集是"温度单通道"**：颜色全由 shader 现算，好处是一张图能表达 900~1900 K；代价是**改色调要改 shader**
   （生成脚本只管形态）。调色温范围时改 `blackbody()` 的三段色，别去重烘图集。
4. **火的形态偏"慢"**：一整个循环 5.2 s，火舌的卷边是慢动作；要更快只改 `LOOP_SEC`（三层速度按倍数跟着走）。
   改太快会在 64 帧之间看出"跳"（每帧 81 ms），所以真要快就得加到 128 帧 —— 那是图集体积翻倍的事。
5. **全屏面板吃掉了"3D 还在"的观感**：18 px 的内边距在 852×348 的横屏上只有 47 物理像素，
   底部那圈常被 HUD 角标（z-9999）压住；要更明显就把 `PAD` 提到 24，但画布宽会掉到 804。
6. **空态提示的折行是顺手修的**（世界层 0 段时宽 1 px，绝对定位那句按 1 px 折成竖排）：老路径同样是这个写法，
   这一版一起修了；`w-max` 之后长句由 `max-w-[min(88vw,520px)]` 兜底。
7. 上一版的风险（splat 桌面残差、GS 资产不进仓库、真机帧率未量、伪多视角 ±6° 硬停）都还在。

### 14.2 load 恒 "-" 的根因与修法（已验到非零毫秒）

**根因**（真 bug，不是读数口的问题）：`GsStep0Environment` 里 `useLayoutEffect(..., [phase])` 在
splat 就绪、`phase` 从 `loading → ready` 时**又跑了一遍**，又调了 `gsMarkEntered()` —— 它把
`GS_LOAD.ready` 清零（`entered` 换成"这一刻"）。`gsLoadMs() = ready - entered` 从此恒 0，HUD 显示 "-"。

**修法**（报告里要求的二选一，取第 1 种，且拆得更干净）：

- 计时那个 effect 的依赖数组**去掉 `phase`**（`[]`）—— 这个组件不会重新挂载，"进工坊"就是挂载那一拍；
- "跳过开场运镜"单独一个 `[phase]` 的 effect（`skipIntroCam()` 自身幂等，phase 翻转重复调用无害；
  `failed` 回退时不跳，旧场景的开场运镜照旧）。

顺带把 HUD 的 `load` 从"秒（两位小数）"改成**毫秒**（`load 4595ms`），与 `gsStep0.gsLoadMs()` 同口径。

| 读数（模拟器 `emulator-5554`，横屏 864×308 视口 / 画布 852×296 CSS） | 改前 | 改后 |
|---|---|---|
| HUD `load` | **`-`**（5 次进工坊全是） | **3864 / 4093 / 4595 / 3278 / 3109 / 3623 ms**（6 次冷进工坊，spz 走 HTTP 缓存的二次进入会明显更短） |
| 渲染像素比（`canvas.width / clientWidth`） | 2.0（window dpr 2.625） | 2.0（不变） |

### 14.3 火：三处观感

**① 烟：硬边 → 软边（`SMOKE_FRAG` 重写）**

上一版的 alpha 是"径向体块 × 噪声阈值"，而径向体块在**面片的上下边**还没衰减到 0
（`length((uv-0.5)*vec2(1.9,1.0))` 在上边只有 0.5），所以烟柱的上、下沿各是一条几何直边 ——
近景里就是一张灰纸。这一版：

- alpha = **fbm（3 个八度噪声）× 径向衰减**，再加一道 `edge` 径向遮罩，**面片四条边上的 alpha 恒等于 0**；
- 每片自己的 **UV 滚动**（`uScroll`）与随机相位（`uSeed`）：两片不会同节奏地"呼吸"；
- 片数 **4 → 2**（性能项），但每片里画上下两团烟 —— 观感上仍是 4 团、draw call 少 2 次。

**② 炭火：16 个点 → 16 块白热炭块**

"看不见"是**两个原因叠着**，只放大尺寸不够：① 上一版把点埋在两根柴的缝里（y≈-0.038，柴顶在 -0.004），
从相机看整排被柴挡住；② `gl_PointSize` 是**物理像素**，默认机位（距火 ~3.7 m）只有 2~4 CSS px。
现在：

- 16 块 **billboard 面片**（在 shader 里用 view 空间的 xy 做相机右/上偏移，不跟 billboard group 转歪）；
- 只放在柴堆**上表面**（y ≥ -0.005），横铺在顶柴长度方向（±0.13 m）；
- 世界尺寸 3~6 cm；**屏上不足 6 CSS px 时按 6 px 兜底**（shader 里用 `uPxPerM / uDpr` 现算）；
- 亮芯 `#fff3d0`、边缘 `#ff7a2f`，2~7 Hz 各自闪烁，外圈自带加色光晕（加色混合下就是轻微 bloom）；
- 另加一片**炭火床加色光晕**（0.42×0.22 m，`renderOrder` 19）把柴面烘暖。

**③ 根部蓝焰：掺量 0.75→1.1、阈值 0.14→0.22，并删掉一道"把蓝压没"的门**

第 5 版除了阈值窄，还有一道 `smoothstep(0.8, 0.3, heat)` 的上限门；而图集底床是连续高温（heat≈1），
这道门会把底部整圈蓝**全压成 0** —— 只改混蓝比例是白改。这一版只保留下限（有火才蓝）。
另外，火焰面片 `vUv.y<0.22` 那一段本来就**被柴挡住**（面片 depthTest 开着、下沿埋在柴堆里），
所以再补一片**贴柴面的青蓝加色光晕**（`depthTest=false`，0.34×0.16 m，跟着火闪烁）：
shader 管"露在柴上面的那截"，这一片管"贴着柴面的那一圈"。

**火焰块的账**：draw call 16 → 16（烟 -2、炭火光晕 +1、根部蓝光晕 +1，账面持平）；三角面 < 450；
片元采样 **6 → 4 次**（外焰相邻两帧交叉 + 两层内焰各单帧）。

### 14.4 性能：能量到的都量了；结论是"这一档的瓶颈不在我们改的地方"

**① dpr 上限：main 上早就是 2.0，这一条没有可拿的收益。**

`StudioPage` 的 `<Canvas dpr={[1, 2]}>` 从 2026-10 起就在（R3F 的 `[min,max]` 会把 `window.devicePixelRatio`
夹在 [1,2]）。实测：模拟器 window dpr 2.625 → `canvas.width/clientWidth = 2.0`；真机 window dpr 3.5
同样会被夹到 2.0（"真机当前 3.5"是 `window.devicePixelRatio`，不是渲染器的像素比）。
为了确认填充率是不是瓶颈，做了两组对照：

| 对照 | 画布物理像素 | fps（改后二进制，同一机位） |
|---|---|---|
| 852×296 CSS @ dpr 2.0 | 1704×592 = **1.01 MP** | 59.8（8 次读数 59.3~60.4） |
| 1284×475 CSS @ dpr 2.0 | 2568×950 = **2.44 MP** | 49.2（6 次读数 46.0~52.1） |
| 1284×475 CSS @ dpr 1.5（模拟器 density 240） | 1278×444 = 0.57 MP | 32.1（6 次读数） |
| 1284×475 CSS @ dpr 1.0（density 160） | 852×296 = 0.25 MP | 32.0（6 次读数） |

后三行是**连续同一批**量的，方向却跟"降 dpr 变快"**相反**（dpr 1.5/1.0 比 2.0 还慢），
这说明这一组读数被**量测顺序/宿主机负载**主导 —— 换一次分辨率 WebView 重建、JIT 与着色器缓存重来，
恰好又赶上宿主机别的 agent 在出包。**结论只取一条：模拟器（宿主机 GPU）上量不出 dpr 的收益**；
像素量从 1.01 MP 翻到 2.44 MP 也只掉 ~10 fps，远没到填充瓶颈。

**② 火焰采样 6→4、烟 4→2：模拟器上量不出 fps（在噪声内），账面上只有"2 个 draw call + 小面积采样"。**

| 配置（改后二进制，同机位） | calls | tris | fps |
|---|---|---|---|
| 默认（4 taps / 烟 2） | 111 | 4.25M | 59.8（warm）；同二进制另几次 23.0~56.4 |
| `gsFireTaps=6` + `gsSmokeN=4`（第 5 版火焰对照） | **113** | 4.25M | 28.7 / 27.1（与同批默认 40.4 / 23.0 无法分开） |
| 1.6M（候选截断） | 111 | **3.45M** | 48.4（2.44 MP 下）/ 26.7（1.01 MP 下） |
| 800k（设置页成本档） | 111 | **1.85M** | 53.3（2.44 MP 下） |

**模拟器 fps 的噪声本身就是这一节的结论**：同一份代码、同一机位，在这台机器上从**冷启动 12~19 fps**、
到**热机 23 / 28 / 40 / 56 / 60** 都出现过（宿主机同时跑着十几个 agent）；文档 §13 那个"60 fps"也是同一种
"宿主机 GPU"读数。**所以 1~3 fps 级的收益在模拟器上不可分辨，只能上真机。**

**③ 真机预期收益（按像素/绘制预算估，不是读数）**

- **dpr 上限**：**0**（已经是 2.0；要确认的是真机 `canvas.width/clientWidth` 也是 2.0，不是 3.5）；
- **火焰 6→4**：火焰片最近机位约 120×170 px，省 2 次采样 ≈ **4 万 texel/帧**，中端 GPU 上是 0.01 ms 级 ⇒ **<1 fps**；
- **烟 4→2**：2 个 draw call + 几万像素的填充 ⇒ **<0.5 fps**；
- **结论：这三项加起来到不了 50**。47.4~48.6 → ≥50 需要一个**真正的大头**，而这份场景的大头是 **2M 高斯**。

**④ 2M vs 1.6M（候选常量 `gsStep0.GS_MAX_SPLATS_CANDIDATE`，默认不生效——不擅自降）**

- tris 4.25M → **3.45M（-19%）**；模拟器 fps 不可分辨（26.7 vs 28.0，噪声）；
- 观感（`.tmp-gs-perf/shot-5-1.6M.png` 对照 `shot-1-hud-load.png`）：**房间明显掉点** —— 左墙、炉拱一带
  出现成片噪点/空洞（打包数组是空间顺序，截尾 = 整块房间消失；桌面近处还行）。它不是"画质档"，是"成本对照档"；

### 14.6 风险 / 下一步

1. **真机 fps 这一轮没量到**：手机上一直有游戏在前台（`mCurrentFocus=com.miHoYo.hkrpg/...ComboSDKActivity`），

6. `GS_MAX_SPLATS_CANDIDATE` 只是常量，**没有默认打开**；截断会掉房间（见 14.4-④），要用得先接受观感代价。

## 15. 第 7 版：三档 LOD（均匀抽稀的独立 SPZ）+ 真机四档读数（2026-11-26 · `feat/gs-lod-tiers`）

### 15.1 为什么不能再"截断"

§14.4-④ 那个 1.6M 是**渲染期截断**（`splat.splats.numSplats = 1.6M`）：SPZ 的打包数组是**按空间顺序**排的，
截尾 = 保留前半段空间 = **整块房间消失**（左墙与炉拱成片噪点/空洞，`shot-5-1.6M.png`）。
所以这一版换做法：**对点索引做均匀随机抽样 → 抽样索引升序回排 → gzip 一层 → 三份独立文件**，
用"少一点、但全屋都在"替换"前半段全、后半段没有"。

> ★ 抽样后**回排原空间顺序**是有意的，不是实现细节：渲染器按数组顺序做批处理与缓存，
> 打乱顺序的 spz 在真机上更慢（点数一样、帧率更低）。

### 15.2 抽稀算法与种子（`design/decimate-spz.mjs`）

| 项 | 值 |
|---|---|
| 输入 | `.tmp-gs-step2/scene.spz`（2,000,000 点 / 38,000,016 B / sha256 `0deb84e6…`） |
| 种子 | **42**（`--seed`，mulberry32） |
| 抽样 | **部分 Fisher-Yates**：索引数组原地洗前 k 个 → 取出即"无放回等概率"样本 |
| 回排 | 抽样索引**升序**排序（= 原空间顺序） |
| 输出 | SoA 五个数组各自按抽样后顺序重写；头部**只改 numPoints**（偏移 8），shDegree / fractionalBits / flags 逐字节照抄 |
| 压缩 | `zlib.gzipSync(level 9)` 一层（★ Spark 的加载器按 **gzip 魔数**解外层，裸 NGSP 会报 `Unsupported NGSP version`） |
| 自检 | 解压回来逐字段比对**抽样索引处**与输入全等（切错数组/错一位当场停，而不是等到真机上"房间变成噪点"） |
| 可复现 | 同一 `--seed` 同一 `--tiers` 跑两遍，输出逐字节相同（下表 sha256 可复核） |

**格式要点（踩过的坑）**：SPZ 载荷不是"header + 每点 19 B 交错"，是 **Structure of Arrays**：
`pos@16 (9B/点)` / `alpha@16+9N (1B)` / `color@16+10N (3B)` / `scale@16+13N (3B)` / `rot@16+16N (3B)`。
第一版脚本按"每点 19 B"整块搬 —— 文件长度、点数、头**全对**，渲染出来是**一片彩色噪点**（见 §15.7）。
只支持 `version 2 + shDegree 0`（本资产就是），v3 / 带 SH 的资产**整句拒绝**而不是猜。

输入 / 输出（这一轮的实际产物）：

| 文件 | 点数 | 裸长度（= 16 + 19·N） | gzip 后 | sha256（前 16 位） |
|---|---|---|---|---|
| `workshop-step0.spz`（full，不是本脚本产出） | 2,000,000 | 38,000,016 B | 31,180,000 B | `4eee426794b986c7` |
| `workshop-step0-1.6.spz` | 1,600,000 | 30,400,016 B | 24,798,673 B | `efa2df12434ee097` |
| `workshop-step0-1.4.spz` | 1,400,000 | 26,600,016 B | 21,704,761 B | `836cd42567417d44` |
| `workshop-step0-1.2.spz` | 1,200,000 | 22,800,016 B | 18,611,552 B | `ef682dc33f910685` |

gzip 体积 ≈ 裸数据的 81.6%（三档都一样，说明抽稀没改变数据的可压缩性）。

> ★ `--help` 的坑（2026-11-26 修）：第一版没有这个分支，`--help` 被当普通参数忽略，
> **照着缺省输入真的把三档重写了一遍**（有输入文件时一个错都不报，看起来像成功）。现在在碰输入文件之前返回。

### 15.3 三份文件的结构核对（独立于抽稀脚本）

用一个**不 import 抽稀脚本**的核对程序（`design/validate-spz-tiers.mjs`，只按 SoA 布局自己解码；
`node design/validate-spz-tiers.mjs` → 三档全绿才 exit 0）跑出来的：

1. **头**：三份都以 `1f 8b` 开头（gzip ✓），解开是 `NGSP` / version 2 / **numPoints = 1,600,000 / 1,400,000 / 1,200,000** /
   shDegree 0 / fractionalBits 12 / flags 0x40 / reserved 0；裸长度**正好**等于 `16 + 19·N`。
2. **抽样点全部来自全量文件**：每档按步长随机取 20000 个点，**20000/20000 命中**（位置哈希在 full 里找得到）。
3. **数组没错位**：三档的 mean alpha（211.1）、mean RGB（77.6 / 81.2 / 91.7）、mean scale（65.1）与 full **逐一相同**
   —— 错位一位这三个数立刻会变（第一代脚本那版就是彩色的）。
4. **bbox 的唯一差异是正常的**：full 的 `y` 最大 **5.82**，三档都是 **4.82**；而全量文件里 `y > 4.82` 只有 **2 个点**
   （2,000,000 里）—— 抽稀把这两根"针"丢了，不是空间被截掉。
   ★ 所以核对程序判 bbox **不按固定容差**（1.0 的差看着很大，其实只值 2 个点），而是数
   "full 里落在这一档极值之外的点的个数"，≤ 0.1‰·N 算正常；同时查**包含关系**
   （抽稀造不出 full 里没有的空间）。这条口径本身就是踩出来的：按 3% 边长判，这三个**好**文件会被判红。

**结论**：三份文件是"全屋的等概率子集"，不是截尾、不是错位。这一条必须跑过再上真机（§15.7 的教训）。

### 16.3 "静态火"的真根因：R3F 9.3 的 uniforms 不再按引用传

这一条比"图集 5.2 s 循环"更致命，先写在前面：**上一版（和这一版刚接好时）火的所有噪声都停在第一帧。**

- R3F 9.3 起，`<shaderMaterial uniforms={obj}>` 不再把 `obj` 挂到材质上，而是把值
  `Object.assign` 进材质自己的 uniforms 对象（`@react-three/fiber` 的
  `events-*.esm.js`："ShaderMaterial uniforms must keep a stable target reference"）。
- 而火的动画全靠 `uniforms.uTime.value = t` 推 → 材质里那个 `uTime` **恒为 0**：
  火焰/烟/柴木/热雾的所有噪声停在第一帧，只有 JS 里算的"灯光闪烁"在动。
  于是观感正是主人说的"**会呼吸的静态贴图**"。
- 修法：挂载后把这几个材质的 `uniforms` 换回我们自己的对象（`HearthFire` 的 `useLayoutEffect`）。
  验收读数 `__gsFire.matTime` 必须等于 `__gsFire.uTime`：**修前 `matTime=0`、修后两者同步
  25.384 s**；修好后火焰区域的 200 ms 像素差从 **0.31/255** 升到 **9.21/255**（火像素，见 §16.6）。

### 16.4 火：这一版的结构（按主人给的 5 条逐条落地）

| 要求 | 做法 |
|---|---|
| 实时程序化，不做一次性烘焙 | 运行时用固定种子生成 **32³ 可平铺噪声体素**（`fireSim.makeNoiseVolume`：R = curl 流函数、G = 主体纹理、B = 细节），`Data3DTexture` 上 GPU。**没有一帧是离线烘的**；图集整个删掉（省一次 0.28 MB fetch + 21 MB 显存） |
| 3D curl/涡度 + 上升速度场 + 时间演化 | 着色器里 `curl2()` 取流函数 ψ 的旋度（体素 R 通道，z 轴走时间 ⇒ 涡旋本身在演化）；纹理按 `q.y - uTime*speed` 向上平流（中心列更快）；所有时间项都是 `+uTime`，**没有 `fract`/取模** |
| 至少 3 个频率层 | 一张面片里算 **外 / 中 / 内三层**（各自包围盒 1.0 / 0.86 / 0.6、频率 2.6 / 3.4 / 4.6、上卷速度 0.55 / 0.8 / 1.1、相位 0 / 1.7 / 3.9）；三条火舌各自的摆动用两频正弦（频率互质）⇒ **整团火的相位永不复位**。draw call 3 → 1 |
| 粒子仿真（300~600 颗） | `fireSim.FireParticles`：**420 颗火焰粒子**，真积分 —— 浮力随温度衰减（`0.18+1.15·heat`）、3D curl 涡流、空气阻力、尺寸随时间增大、温度 1→0（白黄→橙→暗红→烟）、寿命 **0.6~1.6 s**；`Points` + 自定义着色器、加色混合 |
| 余烬/火星带物理 | 原 32 颗改成同一套积分器：向上初速 0.7~1.4 m/s、侧向涡流、空气阻力、亮度按寿命衰减 + 每颗自己的闪烁相位；寿命 1.6~3.2 s。与火焰粒子**共用 1 次 draw call**（`aKind` 分支） |
| 光照联动 | 点光强度由**火焰总能量**驱动：每帧把 420 颗粒子的温度求均值（`FireParticles.energy`，8 Hz 指数平滑），`intensity = base × (0.72 + 0.42·energy)`；颜色同时在这条曲线上走。**不再用三频正弦** |

形态细节：三条火舌取并集 + 底部火床 + 一层连续"芯部"（`core`）—— 只靠噪声乘形状的话，
阈值会把火撕成"三根蜡烛"；芯部保证噪声只负责撕边、不负责把火撕没。颜色仍是黑体色温
（`blackbody()`），但上限从 1900 K 收到 **1500 K**（`850 + 650·heat^1.1`）：上一版的黄白芯太大，
这一版让"白"只落在最热的一小块。

★ 图集资产（`public/models/study/tex/fire-atlas.webp`，21 MB 显存那份）这一版**不再加载**；
生成脚本 `design/gen-fire-atlas.mjs` 留在仓库里当历史与对照，运行时零引用。

- 200 ms 的火焰像素差 **9.21 > 8**（要求达标）；3 s 的差 **15.74 > 9.21**，且 B→C 更大
  ⇒ **不是周期重复**（相位只增不减、每颗粒子各自重生，没有"回到上一轮"的帧）。
- 同一份测量的"修 uniforms 前"读数：盒子 0.31 / 火像素 0.74 —— 这就是"静态火"的量化版本；
  修后火像素 200 ms 是 9.21。两组的盒子差都受"区域里 71% 是黑背景"稀释，所以判据看火像素那一列。

### 16.7 面板打开时：火也停

工作流面板是全屏波浪面板，盖住画布时 `StudioPage` 把 canvas 的 `frameloop` 置 `never`。
所以**火和整个 3D 一起停**，这是**有意的设计选择**：

- 面板盖着时 3D 一个像素都不在屏上，继续算 420 颗粒子/噪声是白烧 GPU；这一轮 `__gsAccept.frames`
  在面板打开前后 **1024 → 1024（1.5 s）**，就是"3D 一帧都没画"的证据；
- 面板收起后火从**停住的那一帧**继续（仿真时间冻结、不是重置），所以不会有"收起面板火跳一下"。
  面板那 1.5 s 里 `__gsFire.time` 也停住（读数 15.461 s，与 `__gsAccept.frames` 同拍）。

### 16.8 风险 / 下一步

1. **真机 fps 这一轮没量**（手机被占用）。下一轮真机补：近景 + 默认机位各 3 次，1.6M 同档与
   §15.5 的 42.1 比；若 3D 体素采样在中端 GPU 上比图集采样贵，最坏情况是火焰片元那一小块
   （近景约 120×170 CSS px）多几次 ALU —— 量出来再决定要不要把 32³ 体素降到 24³。
2. **模拟器截图抓不到动起来的 WebGL 层**：本节的"动"是 `readPixels` 量出来的；四张静帧截图
   仍是 `adb screencap`（画布是冻住的那一帧，但内容/角标都是真的）。真机验收建议用真机截图，
   或者先用模拟器 `screenrecord` 的另一套口径（这台 AVD 上不可用）。
3. **近景里的粒子/炭火偏"散景"**：420 颗粒子与 16 块炭的屏上尺寸在很近的机位（≈0.6 m）会到
   十几~上百物理像素，读作光斑。嫌大就调 `PARTICLE_FRAG` 的 `7.0 * uDpr` 上限与 `fireSim`
   的 `baseSize`；不影响"动"的结论。
4. **R3F uniforms 的坑是全局性的**：以后任何 `<shaderMaterial>` 只要在 `useFrame` 里改
   `uniforms.x.value`，都要确认材质 `uniforms` 是不是同一份（本文件 `useLayoutEffect` 是模板）。
   这一轮查过 `src/studio`，原生 `<shaderMaterial>` 只有 `HearthFire` 一处。
5. **粒子预算是 CPU 的**：420 颗 / 60 Hz 的积分 + 3 次解析梯度采样约 0.1~0.3 ms/帧（估），
   没有单独 profile；如果以后加到 1000+ 颗要挪到 GPU。

### 17.2 为什么是 −0.23（而不是别的数）

- **方向**：屏幕右 = 世界 −z（相机在 +x）。火锚点在世界 z≈+0.10，她原来在 −0.03 ⇒ 她在火的
  −z 侧；往 **−z** 让（屏幕右）才能把火让出来。往 +z 是往火上站，实测更挡。
- **量出来的三个约束**（都取自默认机位、真机像素口径）：
  - 她**只露腰以上**：那条遮挡线只由 x（站位离桌沿的距离）决定，z 平移不动它 ⇒ 不变；
  - **仍在壁炉那一侧**：x=−0.82 不变，她还在炉前；
  - 与桌中线偏差 `__gsAccept.npcOffsetM` = **0.212 m**（主人这一轮把上限放宽到 0.25 m）。
- **效果**：火可见像素从 **0 → 1457**（占画布 0.0000% → 0.0409%），无遮挡参考的 **94.5%**；
  炉口被挡的**宽度** 21.3%（逐行量，见 §17.3）⇒ 露出 **78.7%** ≫ 主人要的 1/3。
- ⚠ 这条式子反过来读：z > −0.13 时火开始被她压住（§16 的 z=−0.03 就是 0% 那一档）。

### 17.3 测量口径（这一版的数都是这么来的）

- **截图**：真机全屏 `2800×1272`（竖屏横过来；dpr 3.5、CSS 800×363）；画布 **1576×702 渲染像素**
  （CSS 788×351 @ pixelRatio 2，`StudioPage` 的 `dpr={[1,2]}`）；相机 fov 50。
- **火像素**：火的投影盒（`__gsAccept.fire.screenBox`，默认机位 CSS `[437,88,468,143]`）内，
  `R≥180 且 R−B≥80 且 R−G≥5 且 G≥40` 的像素（亮橙/黄白，排除皮肤、桌面暖光、石头）。
- **过曝白**：`min(R,G,B) ≥ 250`；**白色团块** = 这一阈值的连通域（近景 ROI = 近景机位的火盒
  裁进画布）。"过曝占比"报两种分母：占 ROI、占"亮像素"（`max(R,G,B) ≥ 128`）。
- **炉口被挡**：同一机位、同一份代码，把 NPC 的 `z` 临时挪到 −2.5 截一张**无遮挡参考**，与最终
  站位逐像素比：ROI（火盒左右各留 16/18 px、上下留 43/7 px）里 `max|ΔRGB| > 30` 的像素 =
  被她挡住的；再逐行取"变了的横跨 / ROI 宽"的均值 = 被挡宽度。**这一步只能在浏览器里做**
  （真机包不能运行时挪 NPC；浏览器按同一几何 800×363 @ dpr 3.5 截，画布与真机同为 1576×702）。
