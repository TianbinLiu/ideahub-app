## 0. 结论先说（读完这五条就够开会了）

1. **这条视频的技术栈是「一图 → 世界模型补全多视角 → 高斯泼溅」，工具是 World Labs 的 Atlas**，作者把出来的串流场景导进 Blender 里漫游。视频无字幕，摘要来自标题 / 简介 / 画面 / 评论（§1）。
2. **高斯泼溅是「把照片里的光」烘进几百万个椭球里**：静态、真实、实时，但**不能改灯、不能挑单个物件、不能做动画**。评论区那句「光影是画上去的，涉及动画就没戏」是准确的（§2、§4）。
3. **Atlas 今天可用的口径**：一张图或 8~16 张重叠照片进去，refined 重建 5,000 credits（约 $5）、15~21 分钟，出 SPZ，可直接进 Blender 5.3 / Spark（Three.js）；draft 500 credits（约 $0.5）先验几何。视角 / 视频帧的单价**官方没公开**，所以预算上限不确定（§5）。
4. **最要命的一条不是技术是条款**：免费账号的产物归 World Labs、只许个人非商业使用，且**账号状态按生成那一刻判定**。我们的游戏是要上架变现的 → 要么买 credits 用付费账号重建，要么走「自己拍自己的桌子」这条路（§5、§10）。
5. **我们的场景只该重建「静态、哑光、有纹理」的那一半**：桌子、椅子、书架、壁炉、台灯、地毯、墙画、摆件。人物（4 个角色位 + 铸卡师 + 玩家手臂）、卡牌、投影光、全息、玻璃窗与窗外夜景，**一律不进 splat**（§6）。

评论区（30 条热门）基本围着四件事转：

- **怎么进去**：一堆人卡在验证码 / 手机收不到短信（「体验地址一堆验证码输完还是进不去」「网站要电话才能进 但是我又收不到短信」），有人回「邮箱不用国内的能直接进」「联通 / 5sim」。
- **多少钱**：25 赞的一条直接贴了链接并写「新注册可以免费生成一次，定价有点贵」；另一条说「最多 24 张图，记得要花 5000 积分导出训练高斯模型」——**这条和今天的官方文档对不上**（文档写 refined 收 2~512 帧、单房间推荐 8~16 视角），要么是当时的旧限制，要么是记错了，按旧说法规划预算会出错。
- **能不能改 / 能不能动**：问「光影能改变吗」「能做成多边形模型方便 Blender 编辑吗」「场景内不能 rig 是硬伤」。回答一致：静态、光烘死在颜色里、不能 rig；「Blender 的高斯可以做到一定程度打光，但效果不太好」；有人的结论很实用：「只生成不需要 rig 的部分，需要 rig 的物体另外建」。
- **精度**：点赞最高的抱怨是「这种泼溅生成的场景还没有实用价值吧，只能拿来当壁纸」；11 赞的补刀「远看还行，不能近看，最后还是要手搓」；另一条指窗景「离得太近就像一张贴图」。反驳的声音也有：「拿来做固定场景一致性会非常好」「作为美宣完全够用，所有工具加入工作流都需要深加工」。

**对我们要紧的三句话**：① 这门技术今天的最佳用途是「固定的、静止的、有质感的布景」，正好是工坊那张桌子；② 它的短板（不能动、不能改灯、近看糊、窗外假）会**在我们把镜头推近桌面时全部暴露**，所以取舍必须提前定；③ 视频作者自己都把产物导进 Blender 再处理 —— 中间那道「清理 / 对齐 / 拆分」的活儿是省不掉的。

## 2. 高斯泼溅（3D Gaussian Splatting）是什么

一句话：**用几百万个带方向与颜色的小椭球（各向异性高斯）去表示一个场景，渲染时把它们投影到屏幕上按深度排序、逐个 alpha 混合**。

- 出处：Kerbl、Kopanas、Leimkühler、Drettakis，*3D Gaussian Splatting for Real-Time Radiance Field Rendering*，SIGGRAPH 2023（[arXiv:2308.04079](https://arxiv.org/abs/2308.04079)；参考实现 [graphdeco-inria/gaussian-splatting](https://github.com/graphdeco-inria/gaussian-splatting)）。
- 每个高斯存的量：中心位置 3 + 旋转四元数 4 + 缩放 3 + 不透明度 1 + 颜色（3 阶球谐，48 个系数）= **59 个浮点**。所以一个 200 万高斯的场景，原始 `.ply` 是**几百 MB 量级**（这是量级估算，不是实测）。
- 训练：从一组**已知位姿**的照片出发，用可微光栅化把渲染图与原图对像素，反传更新每个高斯的参数，顺便做「致密化 / 剪枝」。论文与后续实现的量级都在**单卡几十分钟、3 万次迭代**（不同实现、场景差异很大）。
- 渲染：不是光线追踪也不是光线步进，是 **tile-based 的 splatting**（按屏幕分块、每块排序后混合）。所以它**快**（桌面 1080p 实时），也所以它**吃填充率和显存**（这正是手机端的瓶颈）。

### 与 NeRF / 传统 3D 的差别（选型就看这张表）

| | NeRF（2020 起） | 3DGS（2023 起） | 传统建模 / 摄影测量 |
|---|---|---|---|
| 表示 | 隐式：MLP 把 (x, 方向) 映射成密度与颜色 | 显式：一堆高斯 | 显式：网格 + 贴图 |
| 渲染 | 光线步进，慢；原版几秒一帧 | 光栅化，实时 | 实时，但靠多边形预算 |
| 训练 | 几小时（原版） | 几十分钟 | 不需要训练，要人做 |
| 新视角质量 | 好，尤其视角内插 | 好，高频细节更强 | 取决于建模水平 |
| 几何 | 有密度场，表面发虚 | **表面发虚**（不是网格，没有"面"） | 精确、可编辑、可物理 |
| 改灯 / 改材质 | 改不了（也是烘进去的） | 改不了（烘进颜色） | **随便改** |
| 挑单个物件 / 做动画 | 不行 | 不行（只能按空间裁） | **可以** |
| 引擎集成 | 麻烦 | 需要专用渲染器，但生态已经齐了 | 原生 |

★ **一句话选型**：要「真、快、静态的布景」→ GS；要「能动、能改、能进物理」→ 传统网格。**别指望用 GS 做游戏资产**，它更像「一张会透视的背景画」。

### 它现在被用在哪

房产 / 展陈的可漫游实景、影视与游戏的美宣与背景板（视频评论区就是这拨人）、电商单品 360°、具身智能的仿真场景。**共同点：静态、固定光、近看不过分。** 这也划出了我们的用法边界。

## 4. 坑（按"会不会毁掉我们这张桌子"排序）

1. **动态一律不行**。人、车、窗帘、火、水、树叶、屏幕内容，只要在拍的时候动了，重建出来就是拖影 / 双影。工坊里的**炉火、投影光、卡牌翻面、全息**都属于动态 —— 这些必须是实时特效或贴图，不能指望 splat。
2. **光照是烘死的，改不了**。颜色里已经含了当时的阳光和灯。想要"白天 / 夜晚 / 情绪光"三套，就是三套重建（成本 ×N）；Atlas 有 Relight、Blender 里也能"一定程度上打光"，但都属于二次加工，**效果无保证**（评论区的实测说法是「效果不太好」）。
3. **反光与透明是重灾区**。玻璃、镜面、亮面木桌、金属、水面：高光在不同视角下"不守恒"，重建会得到一层漂浮的雾或重影。对策：偏振镜、哑光喷剂（AESUB 一类）、拍摄时避开镜面角度、或者**干脆用网格做**（我们的桌面要放卡牌与投影，桌面千万别选高光材质）。
4. **纯色 / 白墙 / 无纹理面**。位姿估计找不到特征点，墙面会"起包"或干脆对不齐。Atlas 文档把「大面积平墙」单列为要重点检查的项。对策：挂画、贴标记、搬东西（我们本来就有书架和挂画，这是优势）。
5. **薄结构会断**。桌腿、线缆、吊灯杆、椅子横档：要么缺一截，要么糊成一团。赛博朋克方向（D）满桌线缆，是最难的一项。
6. **天空 / 树 / 远景 / 窗外**。Atlas 文档明确列为易坏项（条纹、团块、漂浮物）。B 方向整面落地窗 + 城市夜景，正是靶心 —— 窗景应该用贴图或视频，splat 只做室内。
7. **尺度是任意的**。SfM 出来的场景没有"米"，Atlas 的坐标系也不是我们的 `TABLE = { w: 16, d: 7 }`。**必须在 Blender 里用一个已知长度对齐**（见 §7 第 6 步），否则卡位永远贴不准。
8. **不能挑单个物件**。splat 里没有"椅子"这个概念。要分物件，只能在 SuperSplat / Blender 里**按空间裁成多份**，各存一个文件、各自加载。
9. **和网格混排有深度问题**。splat 之间不做 z-buffer 遮挡，与不透明 mesh 相交时会"透出来"。卡牌、卡位这些**必须摆在 splat 之上**：抬高一点点、或者把 splat 当纯背景层、或者先画 mesh 深度再画 splat。
10. **手机上的成本是真的**。200 万高斯在桌面上无压力，在 WebView 里是几十万级的预算（数量级估算，未在真机实测）。我们连**卡面贴图**都限宽 512、进视口才上传 GPU（`docs/workshop-game-design.md` §2.6b），splat 该照同一条纪律：先裁、再切、再压、按距离 LOD。

## 5. Atlas（atlas.worldlabs.ai）怎么用、什么限制

> 核实状态：**官方文档（docs.atlas.worldlabs.ai）为主，已逐条读过**；网页 Studio 需要登录，我这边没有账号，**登录后的界面与免费额度未核实**；下面凡是二手报道的会标出来。

### 5.1 它是什么

World Labs（李飞飞那家）的「omni 世界模型」。2026-09 以受邀制预览发布，**2026-11-12 向所有人开放**（[Creative AI News 的报道](https://www.creativeainews.com/articles/world-labs-atlas-open-photo-to-3d-set-cost-2026/)）。今天它不是一个按钮，而是**同一套模型上的几件工具**：

| 工具 | 输入 | 输出 | 对我们有没有用 |
|---|---|---|---|
| **Viewfinder** | 1 张图（模型补全房间）或 8~16 张重叠照片 | 可漫游的场景、相机路径视频、3D splat | **主用**：概念图或实拍照片 → splat |
| **Chisel** | 简单体块 + 文字 / 参考图 | 重新绘制的场景 | 备用：先摆体块定比例再做美术 |
| **Splats to Mesh** | splat | 多边形 mesh | 需要碰撞 / 引擎原生管线时用（有损） |
| **Relight** | 已有 splat + 新光 | 重新打光的 splat | 想改灯时试（按模型计费，效果无保证） |
| **Frameboy** | 完成的场景 | 浏览器里云端实时漫游（研究预览，$0.5 / 分钟） | 只看，不进游戏 |

另外有 Developer API、CLI（`worldlabs`）、MCP（可在 Claude 里用）、Blender 集成、开源渲染器 **Spark**。

### 5.2 一条图的典型流程（官方文档的步骤，也是我们该走的）

1. **位姿**：`images2PosedRGBD` —— 给每张图估相机位姿 + 深度图，可指定 `targetResolution`（1280×720 / 960×720 / 528×704 / 720×1280 之一）。
2. **补视角**：`atlasGenerate` —— 把已有帧当 `contextFrames`，给 6~12 个新相机位，`returnDepth: true`。单张图能"忠实"的极限大约是**半个视场角**或**约三分之一景深**的位移，超出部分模型开始编。相邻视角**重叠约 50%**（文档说 10% 是实操下限）。
3. **查一致性**：每个新视角都要看。桌上的物件在两个视角里形状 / 位置不一致 → 最终就是重影（文档举的例子正是"同一张餐桌在两个视角里不一样，重建成两张桌子叠着"）。**出现不一致，删掉那一帧，别硬着头皮往下走。**
4. **重建**：`posedImages2Splats` —— 每帧都要「图 + 相机 + 深度」，所有帧同一网格。
   - **draft**（`refine: false`）：2~32 帧，500 credits（约 $0.5），约 30 秒，出一个 `draftSplat`。
   - **refined**（默认）：2~512 帧，5,000 credits（约 $5），2~32 帧约 15~21 分钟、33~512 帧最多 30 分钟，出 `refinedSplats`（按高斯数给多个 SPZ）。**失败免费**。
   - 官方推荐单房间 **8~16 个分布均匀的视角**；draft 用来先验几何与覆盖，觉得对再 refined。
5. **拿走**：SPZ 直接给 Spark（网页）或 Blender 5.3（拖进视口即可，官方有 Blender 指南）；要网格就再走 `splats2Mesh`。

## 6. 我们工坊：哪些能重建、哪些不能

现状（读代码得到，不是猜的）：`TableScene` 是一张 `TABLE = { w: 16, d: 7 }` 的长桌，桌上有 **4 个角色位 + 1 个场景位**，相机是第一人称眼位（玩家手臂那具粗糙模型已摘掉，NPC 铸卡师仍在），横屏优先，卡面是 512 宽的贴图、深色 UI + 品牌蓝（`docs/g1-scene-plan.md` §0、`docs/workshop-game-design.md` §2.6/§2.6b）。

### 6.1 适合重建（静态、哑光、有纹理）

| 物件 | 为什么适合 | 注意 |
|---|---|---|
| 长桌本体 | 主体、占画面最大、纹理足 | **别做高光清漆面**；桌面与卡牌会有深度冲突（§4.9） |
| 椅子（4~6 把） | 木质 + 布面，哑光 | 腿是薄结构，拍/生成时要有近景 |
| 书架 / 墙板 | 纹理最丰富，GS 的舒适区 | 整面书脊重复，远景会糊成一片，见 §8-A |
| 壁炉（石砌） | 哑光、纹理足、静态 | **火不能进 splat**，火焰单独做 |
| 台灯 / 吊灯 | 造型简单、金属不过分 | 灯罩若透光会穿帮；灯泡是发光体 |
| 地毯 | 织物纹理，GS 表现好 | 边缘与地板交界处要检查 |
| 墙上挂画 / 摆件 | 小、静、有细节 | 想单独动它们就别进同一张 splat |

### 6.2 不适合（现在就不要写进需求）

| 东西 | 为什么不行 | 该怎么办 |
|---|---|---|
| **人物**（4 个角色位、铸卡师 NPC、玩家手臂） | GS 不能 rig、表情/动作全废；Atlas 文档也把「人脸细节」列为不可靠 | 继续用现有 3D 模型 / Live2D / 立绘 |
| **卡牌** | 要清晰文字、要换面、要能被点、要淡入淡出（§2.6b） | 继续用 mesh + 贴图，**永远不进 splat** |
| **投影光 / 体积光 / 全息** | 是渲染出来的光，不是几何；在全息的情况下还是动态的 | 继续用 shader / 面片 |
| **玻璃窗 + 窗外夜景**（B 方向） | 官方明确列为易坏项；玻璃与窗外会互相打架，霓虹反光不守恒 | **不进 splat**：窗框 / 玻璃 / 窗外用网格 + 材质 + 真灯补（混合方案见 §9），splat 只做室内这半边 |
| **炉火、烟、水** | 动态 | 粒子 / 序列帧 |
| **大面积纯白 / 纯色墙** | 位姿估计会失败、墙面起包 | 挂画、贴标记，或这面墙用 mesh |
| **镜面 / 亮面金属桌面**（D 方向偏金属） | 高光不守恒，重建出一层雾 | 换哑光材质，或这块单独用 mesh + 环境反射 |

### 6.3 性能与坐标（工程侧的三条硬约束）

1. **一个 splat 文件别装整间房**：按「桌面近景 / 书架墙 / 椅子 / 地毯」切成 3~4 份，按相机距离 LOD 加载。首屏只上 1 份。
2. **坐标系要对齐 `TABLE`**：Atlas 的尺度不是我们的 16×7。在 Blender 里按桌宽 16 单位缩放，导出时把变换烘进去（§7 第 6 步）。
3. **兜底路线必须有**：老机型 / WebView 不支持浮点纹理时，退回现在的程序化桌子 + 一张烘好的全景背景。**不能让"换 splat"变成一次只能在新手机上玩的更新**。

## 7. 从概念图到 Three.js：推荐流程

> 前提：**先拿一张概念图做"最小可验证"**（draft $0.5 这一档），跑通「概念图 → SPZ → r3f 里看得见」再谈美术。

1. **定方向**：四张概念图里挑一张（§8）。挑完把它当"美术基准"，后面所有重建都对着它校色。
2. **准备输入图**：从概念图里裁一张**玩家视角**的主图（1280×720），构图就是游戏里第一眼看到的画面。**只给一张就够**——我们的相机是固定的玩家机位，不需要整个房间转一圈；这刚好落在 Atlas 单图"能保持忠实"的半个视场角里。
3. **Atlas 位姿 + 补视角**：`images2PosedRGBD`（`targetResolution: [1280, 720]`）→ `atlasGenerate` 要 **6~12 个视角**、`returnDepth: true`，相机沿桌子四周、与原始相机同高、都看向桌面。**每个视角都看一眼**，重影的删掉。
4. **draft 验几何**：`posedImages2Splats` + `refine: false`（500 credits，约 30 秒）。看三件事：桌子比例对不对、桌面有没有被"蓬松"成一团、脚下地面有没有洞。不对就回到第 3 步改视角 —— **别在这时候点 refined**（$5 一次，而且第二次还是 $5）。
5. **refined 重建**：同一批 `posedFrames` + 默认 refine（5,000 credits，15~21 分钟）。产出 SPZ（按高斯数可能给多个档）。
6. **清理 + 对齐（Blender 5.3）**：拖进视口 → 删掉边缘浮尘与穿帮 → 按 §6.3 切成几份 → **用一个 16 单位长的参照把桌子对到 `TABLE` 的尺寸** → 记住这个变换（它要写进 Three.js 的 position/scale）。
7. **导出与压缩**：每份一个 SPZ（要碰撞的部分再走 Splats to Mesh 出 GLB）。目标：单文件几 MB、单份几十万高斯（数量级，按真机实测再调）。
8. **进 Three.js**：`@sparkjsdev/spark` + 现有 r3f，`SparkRenderer` + `SplatMesh` 放进 `TableScene` 那个 `<Canvas>`；splat 当**静态背景层**，卡位 / 卡牌 / 投影光继续用 mesh，并抬到 splat 之上避免穿插；按距离 LOD、首屏只加载 1 份。
9. **验收**：① 真机上 60 秒不卡、不发烫；② 卡牌与桌面没有穿插闪烁；③ 四个角落转过去没有"半边塌掉"；④ 老机型走兜底路线仍可玩。

> 另一条路（并行考虑）：**自己搭 / 借一间房拍 8~16 张**。好处是版权干净、材质和光完全可控、能反复拍；坏处是要有人力和场地。技术流程第 3 步之后完全相同。

## 9. 窗户、玻璃与光照：混合方案

> 2026-11-24 补。触发点是主人对 §6.2 那一格的判断：**高斯做的窗户只是贴图 / 烘焙**（没有真实光源、没有玻璃），后续必须补。
> 本节只定方案、顺序与工作量，**不动代码**；引到的 three / Spark 行为都注了是"读源码读来的"还是"没验"（§9.6）。

**读完这三条就够开会**

1. 窗、玻璃、窗外**一律不进 splat**，用「低模网格 + PBR 材质 + 真灯」做；splat 只负责哑光静态的那一半（§9.2）。
2. splat **不吃灯**（`SparkRenderer` 的 `material` 是 `ShaderMaterial`，three 的灯光 uniform 根本到不了它）⇒「GS 怎么吃光」只能在三条路里选：多套烘焙交叉淡化 / dyno 光照调制 / 窗附近让位给网格（§9.3）。推荐 **a + c 做主路、b 只做夜间补光**，首版 **约 10~14 人日** + 重建费约 $10。
3. 顺序是「桌面 + 近景小样（2 人日，先把接缝、排序、玻璃这三件最容易翻车的事验掉）→ 窗与玻璃 → 整间房」，每一步都有可量的验收（§9.4）。

### 9.1 为什么 GS 做不了窗

splat 里每个高斯的颜色是 3 阶球谐（48 个系数），它随**视角**变、不随**光源**变：那一束光在训练时就已经乘进颜色里了，渲染时没有任何一步会拿灯的位置再算一遍，所以"改灯"实际等于"重训"（§2、§4.2）。玻璃要的两样东西它一样都表达不了 —— 反射是"视线关于法线镜像出去看到什么"、透射是"视线按 IOR 折射进去看到什么"，而 splat 没有法线、没有 BRDF、没有折射率，只有"从我这个方向看过去有多亮"这一次 α 混合。窗外那半边还额外要「无限远 + 高动态」：相机一动，窗外的视差和玻璃上的反光位置都该跟着动，烘死的颜色不动 —— B 站评论区那句「离得太近就像一张贴图」说的就是这件事，Atlas 文档也把玻璃 / 窗外单列为易坏项（§4.6）。

★ 一句话：**splat 是一份"从这些视角看过去是什么颜色"的采样，不是一个能被重新打光的表面**。窗、玻璃、窗外不是"GS 做得糙"，是它根本没有表达它们的项。

### 9.2 混合方案：GS 管哑光，窗与光走真网格

| 层 | 用什么做 | 关键参数 / 做法 | 为什么不能留在 splat 里 |
|---|---|---|---|
| 哑光静态表面：墙、木梁、书墙、织物、地毯、摆件 | **splat**（SPZ + Spark `SplatMesh`） | 按 §6.3 切 3~4 份，单份几十万高斯；LOD 按相机距离 | 这类表面的全部优势都在这儿：纹理细、静态、近看不过分较真 |
| 窗框 / 窗棂 / 窗台 | **低模网格 + PBR**：`splats2Mesh` 出一版再手工清（细结构会塌，§3 末行），或直接按量的尺寸建 | 木纹走 sRGB 贴图 + 粗糙度贴图；`metalness: 0`；**别省倒角** —— 窗棂那条硬边正是窗光投影的来源 | 要接 `DirectionalLight` 的投影 ⇒ 必须是会写深度的网格 |
| 玻璃 | `MeshPhysicalMaterial` 的透射（不是 `transparent` 半透明） | `transmission: 1`、`ior: 1.52`、`thickness: 0.006~0.01`、`roughness: 0.05~0.1`、`attenuationColor` 略偏青；要色散再加 `dispersion: 0.01~0.02`（手机上关掉）。另一条路是 drei 的 `MeshTransmissionMaterial`，代价见 §9.5-2 | 反射与折射必须**随视角变**，splat 的颜色不随灯变、也没有折射率 |
| 窗外 | **视差板 / skybox / 一段视频纹理**（推荐：远层天空渐变 + 近层城市剪影两层视差；与 §8-B「新海诚式天空光」最搭的是**视频纹理 + 天空渐变**，亮部与色温对得上） | 面片必须 **`transparent: false`**（理由见 §9.5-2）；视频纹理 ≤ 1280×720、≤ 3MB、20~30 秒循环、`muted` + `playsInline` | 窗外是"无限远 + 高动态"，重建必糊（§4.6） |
| 光 | `DirectionalLight`（带阴影）+ `RectAreaLight`（窗面泛光，**不投影**）+ 环境贴图（HDRI → PMREM） | 见 §9.2.2 的三个参数 | splat 不吃灯（§9.2.1），灯只对网格与材质生效 |
| **桌面**（要拍板） | 建议**改成哑光 PBR 网格**，纹理从 splat 里烘或从概念图取 | `roughness: 0.55~0.75`、`metalness: 0`；桌面本来就与卡牌有深度冲突（§4.9），换成网格顺手解决 | 要"窗光落在桌面上、有窗棂的影"，桌面就必须是网格 |

★ **一条必须先拍板的边界**：这张表与 §6.1 把「长桌本体」列为"最适合重建"是**冲突的**。理由在 §9.2.1 —— 桌面留在 splat 里，窗光就永远照不到它，第 1 步的验收（"窗光在桌面上有方向"）也就永远过不了。所以要么桌面改网格（推荐，顺带解决卡牌穿插），要么明确接受"桌面上的光是画上去的、不随窗变"，把验收标准改成"桌面亮度与窗外亮度一致"。**这两条只能选一条。**

#### 9.2.1 splat 不吃灯（这条决定了后面所有选择）

读 `@sparkjsdev/spark@2.4.0` 的类型：`SparkRenderer extends THREE.Mesh`，它的 `material` 是 `ShaderMaterial`（`readonly material: THREE.ShaderMaterial`）；而 three 只对"真的要灯光"的材质上传灯光 uniform，`ShaderMaterial` 要自己显式开 `lights: true` 才算 —— Spark 没有开。所以 `TableScene.tsx:1792-1796` 今天那四盏灯（ambient 0.2 / directional 0.32 / 两盏 point）在换到 splat 之后，**一盏都不会照到 splat 上**；它们只对网格生效（`MagicStudy` 里那些烛光 / 火把同理）。

这不影响现在的桌面（全是程序化 mesh），但它把整件事定死了：**凡是"要被灯照、要接影子、要随窗光变"的表面，都得是网格**。剩下的 splat 那半边，光只能靠"烘进去"或"在 shader 里乘一个系数"（§9.3a / §9.3b）。

#### 9.2.2 灯怎么摆（三个具体参数）

- **`DirectionalLight`（管方向与影子）**：位置按窗口外的太阳方向给，`target` 放在桌面中心；`castShadow`、`shadow.mapSize` 手机 1024 / 平板 2048；`shadow.camera` 的框**收紧到"窗 + 桌面"那一块**（框整间房等于把有限的阴影像素摊薄，窗棂的影就糊了）；`shadow.bias ≈ -0.0005`、`normalBias ≈ 0.02`（薄投影最容易出 acne 与 peter-panning，这两个数要在第 1 步现调）。
- **`RectAreaLight`（管"窗面本身在发光"那层泛光）**：`width/height` 按窗洞实际尺寸、朝室内。三条硬限制都是源码头注释里的：**不支持阴影**、**只支持 PBR 材质**、**必须 `RectAreaLightUniformsLib.init()`**（WebGL 下不 init 就是黑的）。强度以 nit 计，具体值对着曝光调，别抄。
- **环境贴图**：HDRI → `PMREMGenerator` → `scene.environment`。金属（台灯、壁炉附件）与玻璃的高光全靠它。**今天已经有一张，但不是这一张**：`MagicStudy` 的 `StudyEnv` 把 `/models/study/night.hdr` 挂到 `scene.environment`、`environmentIntensity 0.35`（`MagicStudy.tsx:64-77`）—— 那是**夜景**的 HDR、强度还被压到 0.35，窗光要另配一张（白天 / 窗光方向），而且要留意 `StudyEnv` 卸载时会把 `scene.environment` 清成 `null`：**同一个字段别有两个主人**，新加的那张要么接管、要么挂在 `TableScene` 里统一给。反射优先靠这一张（便宜、稳）；"窗外亮块映在桌面 / 玻璃上"那种**屏幕空间反射（SSR）**能补，但要多一趟全屏 pass + 新依赖（drei / postprocessing），首版不上，留在风险里。

### 9.3 GS 怎么"吃"动态光（三条路 × 代价 × 人日）

工作量口径：1 人、含自测与真机走一遍，**不含**等 Atlas 的机时；人日是估算，不是承诺。

#### a. 不打光、只换烘焙：2~3 套 splat + 运行时交叉淡入淡出

**做法**：同一位姿、同一批输入，按不同光照条件出 2~3 套（**分别在不同光下重建 / 重拍**，而不是事后 relight —— §4.2 的实测说法是 Relight"效果不太好"）；每套一份 SPZ、切分与坐标**完全一致**（同一个表变换，否则切的时候会错位）；运行时两套同时在场景里，动 `SplatMesh.opacity`（Spark 2.4 就有这个属性）+ `recolor` 补一点色温差，300~600ms 淡完再把旧的那套卸掉。

**代价**：体积 ×N、淡的那 0.6 秒显存峰值 ×2、**只能在 N 个离散状态之间切**（灯位、光强、色温都定死）；★ 两套高斯位置几乎重合，α 不是简单相加 —— 0.5/0.5 那一帧的合成不透明度只有约 `1-(1-0.5)(1-0.5)=0.75`，**背景会透出来一点**，所以验收要看"中途那一帧"，不是两端。

**工作量**：**4~6 人日 / 两套**（每套清理对齐 + 切分压缩 1~1.5 ⇒ 两套 2~3；淡入淡出与加载排程 1~1.5；真机显存与首屏 1~1.5），每多一套 +2~3 人日 + $5 重建费（补视角的费用官方没公开，§5.3）。★ 三条里唯一**不依赖 Spark 内部 shader** 的一条 —— SDK 升版不会把方案打散。

#### b. shader 调制：给 splat 加一个"光照遮罩"

**做法**：Spark 的 `SplatMesh.objectModifiers / worldModifiers` 是**逐 splat 的 GPU 函数**（dyno：入一个 Gsplat，出一个 Gsplat，能改中心 / 缩放 / 旋转 / 颜色 / 不透明度）。拿世界坐标算"这一点离灯多远、在不在灯的体积里"，把一个系数乘到颜色与 α 上。

**代价**：splat 没有法线、没有阴影 ⇒ **只能整体明暗，出不了束状光斑，也出不了窗棂的影子**；`SparkRenderer.minAlpha` 默认 0.5/255，压到很低就被裁掉（这反而是"夜里把远处压黑"的现成闸）；调参全靠眼睛；Spark 升版时 dyno 的 API 要跟着改。

**工作量**：**3~5 人日**（全量）／**1.5~2 人日**（精简版，只做整体明暗）。适合"氛围增减"（台灯呼吸、霓虹），**不适合当窗光的主路**。

#### c. 混合深度：窗附近由网格接管

**做法**：在 SuperSplat / Blender 里把窗那一片（窗洞 + 窗台 + 窗侧 0.5~1 米的地面与桌面）从 splat 里裁掉，那一片全用网格；光在那一片是真光（有方向、有影子），splat 那半边继续是烘死的。

**三个必须做的事**：① **接缝** —— splat 边缘是半透明椭球（α 渐变）、网格是硬边：要么把网格窗套做得比裁切口大一圈压在接缝上，要么用 `objectModifiers` 按"到窗面的距离"给 α 渐隐（过渡带 3~5 厘米）；② **深度** —— Spark 默认 `transparent: true`（走第二趟透明通道）、`depthWrite: false`（不写 Z，SDK 注释自己就写着"开了多半更糟"），所以 splat 只能靠 `depthTest` 被**网格先写下的深度**挡住，顺序必须是"网格（含窗）先画 → 再合成 splat"；③ **像素对齐** —— 窗洞尺寸在 Blender 里从 splat 量出来（不是按概念图估），差 1~2 个场景单位玻璃与裁切口就错开一条缝。

**代价**：要动 splat 资产（重切、重压、重定坐标），窗多了成本线性涨；接缝**永远**有一条，只能做到"1 米内看不出来"。**工作量：4~6 人日 / 首版**，每多一扇窗 +1~2 人日。

#### 推荐组合：a + c 做主路，b 只做夜间补光

| 做法 | 首版人日 | 之后每加一份 | 换来什么 | 什么时候用 |
|---|---|---|---|---|
| a 多套烘焙 + 交叉淡化 | 4~6（白天 + 夜间两套） | +2~3 / 套 | 整套房间的光都变（含 splat） | **主路**：白天 / 夜间 / 暖光三种状态 |
| c 混合深度（窗附近裁给网格） | 4~6 | +1~2 / 扇窗 | 窗光有方向、有影子、能自由调 | **主路**：窗、窗台、靠窗 1 米内的地面与桌面 |
| b dyno 光照调制 | 1.5~2（精简）／3~5（全量） | +0.5 | 便宜的明暗呼吸 | **只做夜间补光**（台灯、霓虹） |

### 9.4 落地顺序与验收标准

> **每一步都在真机上验**（本仓的规矩：合并、出片都只能装机验，splat 的帧率同理）；浏览器里好看不算。

| 步 | 做什么 | 人日 | 验收（可量，过不了就不进下一步） |
|---|---|---|---|
| **0. 桌面 + 近景小样** | 1 份 refined splat（4~6 个绕桌视角，§7 第 3~5 步）+ 桌面改哑光网格 + 1 盏带影的 directional + 一张白天方向的 HDR 环境光（§9.2.2）。**顺便把 §9.5-2 那条「玻璃采不到 splat」先验掉**（放一块玻璃 + 一块不透明窗外板 + 旁边一圈 splat） | 2 | ① 真机 WebView 稳定 30fps、连跑 60 秒不掉帧（记 `renderer.info.render` 的 calls / triangles）；② splat 与桌面网格的接缝，相机推到距接缝 1 米处截图看不出（不出现硬边、也不出现空缝）；③ 卡牌摆在桌上不穿插、点得中（§4.9）；④ 拿掉 splat 后场景仍能用（兜底没被写死） |
| **1. 窗 + 玻璃 + 窗外** | 窗框 / 窗棂低模 + 玻璃 + 窗外视差板（远层天空 / 近层剪影）+ 窗光（directional + rectArea）+ 环境贴图 | 3~4 | ① 窗光**有方向**：桌面亮区在窗那一侧、窗棂的影子落在背光侧且边界清楚（不是一圈糊 AO）；② 玻璃**有反射**：转相机时反射的窗外亮块跟着移动（不是贴死在玻璃上的图）；③ 玻璃**有折射**：透过玻璃看窗外的边缘相对窗框有 1~3px 错位，窗框本身是清晰一条、不是双影；④ 透过玻璃**没有**一片奶白（有 = 撞上 §9.5-2）；⑤ 一扇窗这条链的 draw call ≤ 10 |
| **2. 整间房 + 第二套光照 + 夜间补光** | 按 §7 重建整间房并切分；第二套（夜间）splat + 交叉淡化；夜间台灯 / 霓虹用 b 的精简版补 | 4~6 | ① 白天 / 夜间切换 600ms 内完成，中途不闪黑不闪白，且**中途那一帧**背景不明显透出来（§9.3a 那条 α 数学）；② 冷启动进工坊的首屏时间与今天同一量级（拿今天的数当基线，超了不收）；③ 真机中端机三档都不掉 30fps：静止 / 绕桌 / 开窗光 + 阴影；④ 老机型退回程序化桌面 + 全景板仍可玩（§6.3 第 3 条） |

### 9.5 风险清单

| # | 风险 | 会出现什么 | 对策 / 兜底 |
|---|---|---|---|
| 1 | **splat 与网格的深度排序、穿模** | Spark 默认 `transparent: true`（走第二趟透明通道）+ `depthWrite: false`（不写 Z）⇒ splat 会被**已经写下深度**的网格挡住（`depthTest` 默认开），但它自己不写深度，挡不住之后画的透明物（玻璃、投影光、UI 面片）；而所有 splat 由 `SparkRenderer` **一个 mesh** 统一画出（`SplatMesh` 只是 `Object3D` 上的生成器，不是 three 单独画的 mesh），所以它跟别的透明物谁先谁后**只由那一个 mesh 的 `renderOrder` 决定** | 近景一律网格、splat 只当最远那一层；卡牌 / 投影光 / 玻璃的 `renderOrder` 排成一支固定的队，写死在代码里（别靠贴的先后）；兜底：splat 不进最前的 renderOrder 就永远不会盖住前景 |
| 2 | **玻璃透明 vs splat 半透明的排序** | three 的 `transmission` 只把**不透明**那一批渲进折射用的 render target（`WebGLRenderer.renderTransmissionPass` 里就一句 `renderObjects( opaqueObjects, … )`），而 splat 默认在 transparent 那一趟 ⇒ **玻璃里根本采不到 splat**；玻璃后面没东西时那趟还会把清屏色掺成白 α 0.5（源码 `if ( _currentClearAlpha < 1 ) setClearColor( 0xffffff, 0.5 )`）⇒ 症状是"玻璃里一片奶白" | 窗外必须是**不透明**网格（视频面片保持 `transparent: false`）；玻璃 `thickness` 给小、缺的那点用反射 / 漫反射补。真要让玻璃折射到 splat 只有两条路：drei 的 `MeshTransmissionMaterial`（每帧自己把整场景渲进 FBO 两次，含 splat ⇒ Spark 那一趟也跟着再跑，手机上大概率不可行），或"窗外先单独渲成一张贴图再贴回窗洞"。★ 这条**必须在第 0 步用一天验掉**，它决定玻璃怎么写 |
| 3 | **体积（多套 splat × 场景大小）** | 两套 × 4 份 = 8 个 SPZ；淡入淡出时还要两份同时在显存 | SPZ 压缩 + 按份 LOD + Spark 2.x 的 `paged`（`SplatPager` 按块取，不必一次全进显存）；但**多套光照 = 多棵树 / 多个 pager，不能共用**。预算先定死：单套 ≤ 8~12MB、两套 ≤ 20MB（量级，第 2 步用真机量），超了**减份数**，不要减亮度 |
| 4 | **帧率（真机中端机 30fps）** | 今天这台 Canvas 连 `shadows` 都没开（`StudioPage.tsx:425` 那串只有 dpr / gl / frameloop）—— 开阴影（多一趟 shadow map）、开透射（多渲一趟整场景 + 一张半浮点 target）、把环境光换成白天那张更亮的 HDR，三样都是新开销 | 先量再开：`renderer.info` + 真机三档帧率；不达标按顺序砍：阴影 mapSize → `transmissionResolutionScale`（默认 1.0，可降到 0.5）→ splat 份数 → 关透射改"渲成贴图"那条兜底 |
| 5 | **"窗口贴图化"在美学上被一眼看穿** | 静态贴图在新海诚那套视觉里最假（§1 评论原话「离得太近就像一张贴图」） | 性价比排序：**两层视差板**（远层天空 + 近层剪影，随相机视差移动）< **20~30 秒循环视频纹理**（云、车灯、霓虹）< 真 3D 城市低模。首版选视差板 + 天空渐变，夜景那套再上视频（解码尺寸与体积按 §9.2 那行限死） |
| 6 | **尺度与对齐** | splat 与网格不共用米制 ⇒ 窗框、玻璃与裁切口错开 1~2 个单位 | 复用 §4.7 / §7 第 6 步：在 Blender 里用 16 单位参照对齐、把变换烘进去；窗洞尺寸**量**出来不估 |
| 7 | **兜底路线** | 老机型 / WebView 不支持浮点纹理 | 退回程序化桌面 + 一张烘好的全景（§6.3 第 3 条）。★ 窗与玻璃这条网格路**不受影响** —— 兜底时"窗还在，只是窗外那张板换成静态图" |

### 9.6 核实状态（哪些是读来的、哪些还没验）

- **已读源码核过**：three r180 的 `WebGLRenderer.renderTransmissionPass`（只 `renderObjects( opaqueObjects … )`）、`MeshPhysicalMaterial`（`ior` 默认 1.5、`thickness` 默认 0、有 `dispersion`）、`RectAreaLight` 头注释（不支持阴影 / 只支持 PBR / 必须 init）；`@sparkjsdev/spark@2.4.0` 的 `dist/types`（`SparkRenderer.transparent` 默认 true、`depthTest` 默认 true、`depthWrite` 默认 false、`SplatMesh.opacity` / `recolor` / `objectModifiers`、`paged` / `SplatPager`）。
- **未验**：真机上"阴影 + 透射 + splat"三项同开的帧率；Atlas Relight / 分别重建出来的第二套是否够用；drei `MeshTransmissionMaterial` 在真机上多渲两遍整场景的代价。
- **依赖现状**：`package.json` 里有 `three@0.180`、`@react-three/fiber@9.3`，**没有** `@sparkjsdev/spark`、**没有** `@react-three/drei` —— 第 0 步要各加一个（或不用 drei，按 §9.5-2 的兜底自己写）。

## 10. 需要主人决策的点

1. **重建范围**：先做「桌面 + 近景」的小样（1~2 份 splat，便宜、稳、快），还是直接整间房（好看，但性能、穿帮、$ 都是数倍）？我的建议：**先小样**，一周内能看到真机效果，再决定要不要整间。
2. **版权与预算**：Atlas 免费账号的产物**只能个人非商业用**，且按生成那一刻判定 —— 上架的游戏不能用免费账号的产物。是「买 credits 用付费账号重建（$5/次 + 未公开的视角费）」，还是「自己搭一间房拍（人力换版权干净）」？**这条不定，后面做多少都白做。**
3. **光照要不要可变**：GS 的光是烘死在颜色里的。只做一套暖光（省、稳）／做 2~3 套（成本 ×N）／试 Relight（效果无保证）？工坊里如果有"白天 / 夜晚 / 情绪"的切换，这会直接改变美术方案。
4. **卡牌与投影光的边界**（建议直接拍板不用讨论）：**卡牌、投影光、全息、炉火、人物，一律不进 splat**，继续走 mesh 与 shader。写在这里是为了以后有人提"把卡也扫进去"时有个依据。
5. **窗户与光照路线**（方案全文 §9）：窗、玻璃、窗外三样**不进 splat**，用网格 + PBR 材质 + 真灯补；GS 那一侧在「多套烘焙交叉淡化 / dyno 光照调制 / 窗附近裁给网格」三条里挑组合。我的建议：**a + c 做主路、b 只做夜间补光**，首版约 10~14 人日 + 重建费约 $10；先只做「桌面 + 近景小样」（2 人日）确认 GS 与网格能混起来，再决定要不要整间房。★ 这条同时卡着 §6.1 —— **桌面要不要从 splat 里拿出来做网格**（§9.2 末尾）：留着它，窗光就永远照不到桌面。
